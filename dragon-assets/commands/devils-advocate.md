# /devils-advocate - 魔鬼代言人

**天龙引擎 V7.4批判性思维 Layer 3 - 协作层**

## 功能

在重大决策后自动触发魔鬼代言人，从对立角度审视决策，避免群体思维和确认偏见。

## 用法

```bash
/devils-advocate [decision-id]
```

### 参数

- `decision-id`: 决策ID（可选，不提供则检查最近的决策）

## 自动触发条件

以下场景会自动触发魔鬼代言人：

### 1. 架构决策
- 关键词：`架构决策`、`技术选型`、`系统设计`、`微服务`、`单体`
- Agent：02架构师
- 示例：[@02架构师] 建议采用微服务架构

### 2. 最佳实践声明
- 关键词：`最佳实践`、`best practice`、`standard`、`pattern`
- Agent：任意
- 示例：[@03构建师] 使用React Query是最佳实践

### 3. 高影响决策
- 成本 > $1000
- 工期 > 2周
- Agent：任意

### 4. 缺少反例的分析
- 批判性思维检查发现"考虑反例"维度得分为0
- Agent：任意

## 双线协作协议

### 旧协议（V7.3）
```
[@分析师] → [@架构师] → [@构建师]
```

### 新协议（V7.4）
```
[@分析师] → [@架构师] → [@魔鬼代言人] → [@架构师（回应）] → [@构建师]
```

## 协作规则

### 1. 必经关卡
以下情况必须经过魔鬼代言人：
- ✅ 所有架构决策
- ✅ 所有"最佳实践"声明
- ✅ 所有高影响决策

### 2. 回应机制
- 原Agent必须回应质疑（接受/反驳/修正）
- 反驳必须提供证据
- 修正必须更新决策文档

### 3. 双线并行
- 主线：原任务执行
- 质疑线：魔鬼代言人审查
- 两线独立但同步

## 协作示例

### 示例1：架构决策

```
[@02架构师]: 建议采用微服务架构，支持未来扩展

[@09-01魔鬼代言人]:
质疑点：
1. 团队规模50人，微服务治理能力不足
2. 当前流量1万QPS，单体足够
3. 反例：Uber早期3000+服务导致部署困难
4. 证伪实验：先实现2个微服务，测试治理能力

[@02架构师（回应）]:
修正决策：
- 接受质疑点1和2
- 修正方案：先模块化单体，规模化后再拆分
- 证伪实验：1个月后评估是否需要微服务

[@09-01魔鬼代言人]:
最终判断：⚠️ 需要修正
修正方案可行，继续执行

[@03构建师]: 开始执行模块化单体方案...
```

### 示例2：最佳实践

```
[@03构建师]: 使用React Query是数据获取的最佳实践

[@09-01魔鬼代言人]:
质疑点：
1. 反例：Redux在复杂客户端状态管理场景更优
2. 盲点：React Query假设主要关注服务端数据获取
3. 证伪实验：评估客户端状态管理复杂度

[@03构建师（回应）]:
接受质疑：
- React Query + Redux组合（React Query处理服务端，Redux处理客户端）
- 更新架构文档，明确两套状态管理系统的边界

[@09-01魔鬼代言人]:
最终判断：✅ 修正后成立
组合方案可行，继续执行
```
