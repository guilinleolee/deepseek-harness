# thin-slices-skill

## L0: 一句话描述 (≤15字)
端到端薄片构建，最小功能闭环。

## L1: 使用场景 (50-100字)
每个功能从用户入口到数据持久化构建完整路径，而非逐层平铺开发。适用于新功能开发、复杂系统解耦、验证最小可行产品。核心理念是优先构建可运行的价值闭环，而非堆积半成品。

## L2: 详细文档

# Thin Vertical Slices (薄片开发法)

> **核心理念**: "Deliver value, not half-finished layers."
> 每个薄片必须跨越所有层，从UI到数据库，构建完整功能路径。

## 薄片 vs 分层对比

```
┌─────────────────────────────────────────────────────────────┐
│  分层开发 (Layered Development) - 不推荐                     │
├─────────────────────────────────────────────────────────────┤
│  Step 1: 完成所有API端点                                     │
│  Step 2: 完成所有Service层                                  │
│  Step 3: 完成所有Data Layer                                 │
│  Step 4: 完成前端                                           │
│                                                             │
│  问题: 很长时间后才能看到任何价值                             │
│       最后一层失败会导致全部返工                             │
│       跨层集成风险累积                                       │
├─────────────────────────────────────────────────────────────┤
│  薄片开发 (Thin Vertical Slices) - 推荐                     │
├─────────────────────────────────────────────────────────────┤
│  Slice A: 登录功能端到端 (API+DB+UI)                        │
│  Slice B: 用户资料端到端                                     │
│  Slice C: 搜索功能端到端                                     │
│  ...                                                        │
│                                                             │
│  优势: 每个薄片都有价值                                       │
│       快速验证架构假设                                       │
│       降低集成风险                                          │
└─────────────────────────────────────────────────────────────┘
```

## 薄片规划流程

### Step 1: 识别核心用户路径

```markdown
## 用户路径分析
1. 用户做什么？ → 用户行为链
2. 每个步骤需要什么？ → 依赖识别
3. 最小路径是什么？ → 薄片定义

示例: 电商结账薄片
- [ ] 商品展示 → [ ] 添加购物车 → [ ] 结算 → [ ] 支付 → [ ] 订单确认
最小薄片: 商品展示 + 结算 + 订单确认 (跳过支付模拟)
```

### Step 2: 定义薄片边界

```markdown
## 薄片边界模板
薄片名称: <功能>_<用户场景>

包含范围:
- API端点: <HTTP方法> <路径>
- 数据模型: <表/集合> <字段>
- 业务逻辑: <核心规则>
- 用户界面: <页面/组件>

排除范围:
- 边缘功能
- 优化特性
- 未来扩展

薄片验收标准:
1. 端到端可运行
2. 用户可感知价值
3. 独立于其他薄片
```

### Step 3: 构建薄片

```markdown
## 薄片执行检查清单

前端 (Top-Down):
  □ 页面组件
  □ 用户输入验证
  □ API调用
  □ 响应展示

后端 (Top-Down):
  □ API端点
  □ 输入验证
  □ 业务逻辑
  □ 数据访问

数据库 (Bottom-Up):
  □ 数据模型
  □ 索引
  □ 迁移脚本

集成:
  □ 前后端联调
  □ 端到端测试
  □ 监控埋点
```

### Step 4: 验证薄片

```markdown
## 薄片验证标准
1. 功能完整性: 薄片内的功能全部可用
2. 独立性: 不依赖其他薄片即可运行
3. 价值可见性: 用户能感受到价值
4. 质量达标: 测试覆盖、性能、安全

验证方法:
- [ ] UI操作验证
- [ ] API测试
- [ ] 集成测试
- [ ] 用户验收
```

## 薄片选择策略

### 选择薄片的原则

| 优先级 | 薄片类型 | 选择理由 |
|--------|---------|---------|
| 🥇 | **入口薄片** | 用户第一接触点，快速验证价值 |
| 🥈 | **核心价值薄片** | 产品核心功能，直接体现价值 |
| 🥉 | **依赖薄片** | 被多个薄片依赖，先构建可降低风险 |
| 4️⃣ | **高风险薄片** | 技术/业务不确定性高，先验证 |

### 薄片排序矩阵

```
价值 ↑
|  [2]核心价值  [1]入口薄片
|
|  [4]次要功能   [3]依赖薄片
└────────────────────────────────→ 风险 (依赖性/不确定性)
```

### 薄片大小控制

| 场景 | 建议规模 | 说明 |
|------|---------|------|
| 验证架构假设 | 极小薄片 | 1-2天，核心路径 |
| MVP开发 | 最小薄片 | 1周，端到端可用 |
| 生产功能 | 标准薄片 | 1-2周，完整功能 |
| 复杂系统 | 分解薄片 | 按用户旅程拆分 |

## 薄片反模式

| 反模式 | 描述 | 正确做法 |
|--------|------|---------|
| **半层薄片** | 只完成某层的部分功能 | 跨越所有层 |
| **过早优化** | 在薄片内过度设计 | 聚焦核心价值 |
| **薄片堆积** | 多个薄片并行但未集成 | 一个完成再下一个 |
| **虚假薄片** | 没有用户价值的"薄片" | 确保价值可见 |
| **依赖循环** | 薄片相互依赖无法独立 | 重构依赖关系 |

## 薄片开发工作流

```bash
# 薄片工作流
/thin-slice new <name>          # 创建新薄片
/thin-slice plan <name>         # 规划薄片范围
/thin-slice build <name>         # 构建薄片
/thin-slice verify <name>       # 验证薄片
/thin-slice integrate <name>    # 集成薄片

# 示例
/thin-slice new login-flow
# → Step 1: 用户路径分析
# → Step 2: 定义边界
# → Step 3: 构建端到端
# → Step 4: 验证完整性
```

## 薄片示例：用户认证薄片

```
薄片: auth_basic
边界:
  API:
    POST /auth/login (登录)
    POST /auth/logout (登出)
    GET /auth/me (当前用户)
  Data:
    users table (id, email, password_hash, created_at)
  Logic:
    密码验证 (bcrypt)
    Session管理
  UI:
    登录表单
    用户信息展示

验收标准:
- 用户可登录
- 登录后可访问受保护资源
- 登出后无法访问

构建顺序:
1. 数据库迁移
2. 用户模型
3. API端点
4. 前端表单
5. 端到端测试
```
