# airstrip-one-trigger (Airstrip One 触发器)

## L0: 一句话描述 (≤15字)
找到魔法时刻，让用户爱上你

## L1: 使用场景 (50-100字)
在产品上线后，识别并优化"魔法时刻"——用户第一次说出"哇！"的那一刻。这个技能帮助你设计、测量和优化让用户从"还行"变成"必须推荐"的触发器。

## L2: 详细文档

### 核心概念

**Airstrip One (跑道一号)** 是一个比喻：
- 想象飞机需要的最短起飞跑道
- 你的跑道是用户的耐心和注意力
- 你的目标是让用户"起飞"——进入推荐和付费的自动巡航状态

**魔法时刻 (Magic Moment)**：
- 用户第一次真正感受到产品价值的瞬间
- 不是"可以"不是"还行"，而是"哇！"
- 这个时刻越早到达，用户留存越高

### 找到魔法时刻

**第一步：追溯用户说出"哇"的时刻**

```
问自己/用户: "在使用产品的过程中，你什么时候第一次感到'这产品真的很棒'？"

记录用户回答:
1. ___
2. ___
3. ___

如果没有用户说过"哇"：
→ 你的产品可能还没有让人"哇"的价值
→ 回到idea-pressure-test重新验证
```

**第二步：测量魔法时刻到达率**

```
公式: 魔法时刻到达率 = 到达魔法时刻的用户数 / 总注册用户数

测量方法:
1. 在关键动作处埋点
2. 追踪用户从注册到第一次"关键行为"的时间
3. 计算到达率

目标:
✅ 优秀: >50%的用户在第1次使用中到达
✅ 良好: 20-50%的用户在第1次使用中到达
⚠️ 需改进: <20%的用户到达
❌ 危险: 用户很少到达，说明onboarding有问题
```

**第三步：加速到达魔法时刻**

```
原则: 删除到达魔法时刻前的所有摩擦

当前路径分析:
注册 → ___ → ___ → ___ → 魔法时刻

问题诊断:
- 步骤太多？ → 删除不必要的步骤
- 引导不清？ → 优化onboarding
- 价值不明？ → 改进新用户引导文案
- 阻力太大？ → 降低使用门槛
```

### 设计触发器

**三种触发器类型**

| 类型 | 描述 | 例子 | 适用场景 |
|------|------|------|---------|
| **Push触发** | 主动推送给用户 | 邮件/推送通知 | 到达魔法时刻后X小时 |
| **行为触发** | 用户做某个动作后触发 | 弹窗/提示 | 完成关键动作后Y分钟 |
| **时间触发** | 固定时间点触发 | 定时邮件 | 注册后第Z天 |

**触发器设计框架**

```
触发器设计 = 触发条件 + 触发内容 + 触发时机

示例1: Push触发器
├── 触发条件: 用户到达魔法时刻后2小时
├── 触发内容: "你体验到[核心功能]了吗？"
└── 触发时机: 到达魔法时刻后2小时

示例2: 行为触发器
├── 触发条件: 用户完成第一次关键动作
├── 触发内容: "太棒了！你已经完成了第一步！"
└── 触发时机: 关键动作完成后立即

示例3: 时间触发器
├── 触发条件: 注册后第3天，未完成核心动作
├── 触发内容: "嗨，回来看看这个功能..."
└── 触发时机: 注册后第3天上午10点
```

### Onboarding优化

**魔法时刻前置化策略**

```
目标: 把魔法时刻从"第5次使用"移到"第1次使用"

策略1: 预填充魔法时刻
- 不要让用户从头开始
- 给他们一个已经"部分完成"的状态
- 例如: 新用户注册后看到已经有人用他们公司的数据

策略2: 跳过非必要步骤
- 推迟所有不影响核心价值的步骤
- 让用户先体验价值，再补充信息
- 例如: 先让用户看到分析结果，再要求填写公司信息

策略3: 直接展示价值
- 第一屏就展示产品最棒的部分
- 不要藏着掖着
- 例如: 不展示"功能列表"，直接展示"分析报告示例"

策略4: 渐进式引导
- 只在用户需要时展示帮助
- 不要一开始就show ALL the features
- 例如: 用户卡住了再弹出帮助，而不是一开始就弹教程
```

### 测量和迭代

**核心指标追踪**

```yaml
魔法时刻到达漏斗:
  注册用户 → 完成关键动作 → 到达魔法时刻 → 变成活跃用户 → 推荐他人
     100%              60%              40%              25%             10%

关注点:
- 哪个环节流失最多？ → 重点优化
- 到达魔法时刻后留存率？ → 验证魔法时刻是否正确
- 到达后推荐率？ → 验证魔法时刻是否足够"魔法"
```

**A/B测试框架**

```
测试1: Onboarding长度
├── A组: 5步onboarding
├── B组: 2步onboarding（直接到核心功能）
└── 指标: 魔法时刻到达率

测试2: 魔法时刻前置
├── A组: 到达后才看到价值示例
├── B组: 注册后立即展示价值示例
└── 指标: 注册到激活的转化率

测试3: 触发器时机
├── A组: 到达魔法时刻后2小时触发
├── B组: 到达魔法时刻后24小时触发
└── 指标: 活跃度保持率
```

### 关键心态

> **魔法时刻不是功能，是体验**。用户不关心你有多少功能，他们关心的是：这个东西能不能在最短时间内让我觉得"这值了"。把资源投入在让一个功能做到极致，而不是做10个功能每个都60分。
