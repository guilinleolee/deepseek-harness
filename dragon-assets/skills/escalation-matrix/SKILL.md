## 核心概念

### 什么是组织镜像4标准？

老金提出的组织设计4个判断标准：

```
┌─────────────────────────────────────────────────────────────┐
│ 组织镜像4标准                                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 1. 明确分工                                                 │
│    → 谁产出，谁判断，谁复核，谁升级                          │
│                                                             │
│ 2. 明确升级路径                                             │
│    → 出了问题往哪里抬？                                      │
│                                                             │
│ 3. 明确复核点                                               │
│    → 哪些节点必须复核？                                     │
│                                                             │
│ 4. 明确兜底点                                              │
│    → 兜不住时谁接管？                                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 升级路径定义

**升级** = 当前层级无法处理，转移到更高层级处理。

```
升级 ≠ 甩锅
升级 = 专业的事交给专业的人
升级 = 保护当前执行者不过载
升级 = 确保问题不被遗漏
```

## 升级路径设计流程

### 5步法

```
Step 1: 失败模式分析
├── 识别所有可能的失败模式
├── 分析失败原因和责任层级
└── 输出: 失败模式清单

Step 2: 升级层级设计
├── 确定升级层级数量（通常3-5层）
├── 定义每层的职责和能力
├── 明确每层的授权边界
└── 输出: 升级层级定义

Step 3: 升级触发设计
├── 定义每种失败模式的触发条件
├── 设定升级阈值和指标
├── 设计升级判断流程
└── 输出: 升级触发矩阵

Step 4: 兜底协议设计
├── 定义最高层级的兜底责任
├── 设计兜不住时的最终处理
├── 明确兜底后的复盘要求
└── 输出: 兜底协议

Step 5: 闭环验证
├── 模拟各种失败场景
├── 验证升级路径有效性
├── 测试兜底协议可行性
└── 输出: 升级路径验证报告
```

## 升级触发矩阵

### 触发条件类型

```yaml
trigger_types:
  - type: "retry_exceeded"
    description: "重试次数超限"
    level: 1
    condition: "重试次数 > [阈值]"
    action: "升级到Level 2"

  - type: "time_exceeded"
    description: "时间超限"
    level: 1
    condition: "执行时间 > [SLA阈值]"
    action: "升级到Level 2"

  - type: "error_type"
    description: "特定错误类型"
    level: 1
    condition: "错误类型 in [黑名单]"
    action: "立即升级到Level 2"

  - type: "impact_level"
    description: "影响范围超限"
    level: 1
    condition: "影响范围 > [阈值]"
    action: "升级到Level 3"

  - type: "unknown_issue"
    description: "未知问题"
    level: 1
    condition: "无法诊断根因"
    action: "升级到Level 3"

  - type: "cross_system"
    description: "跨系统问题"
    level: 2
    condition: "影响多个系统"
    action: "升级到Level 3"

  - type: "business_decision"
    description: "需要业务决策"
    level: 3
    condition: "需要业务判断"
    action: "升级到Level 4"

  - type: "resource_constraint"
    description: "资源约束"
    level: 3
    condition: "需要资源调配"
    action: "升级到Level 4"
```

## 兜底协议设计

### 兜底场景类型

```yaml
fallback_scenarios:
  - type: "max_level_reached"
    description: "达到最高升级层级仍无法解决"
    action: "启动紧急响应流程"
    recovery: "问题升级到人工处理"

  - type: "all_attempts_failed"
    description: "所有自动修复尝试失败"
    action: "触发降级/熔断"
    recovery: "手动介入"

  - type: "unrecoverable_state"
    description: "系统进入不可恢复状态"
    action: "启动灾难恢复"
    recovery: "回滚/切换"

  - type: "circular_escalation"
    description: "循环升级（踢皮球）"
    action: "强制指定处理者"
    recovery: "指定L4负责人处理"

  - type: "timeout_without_response"
    description: "升级后无人响应"
    action: "超时升级到更高层"
    timeout: "Level 2: 5min, Level 3: 10min, Level 4: 30min"
```

## 组织镜像4标准完整实现

### 标准1: 明确分工

```yaml
division_of_labor:
  # 谁产出
  responsible:
    - role: "执行者"
      accountable_for: "具体产出"

  # 谁判断
  accountable:
    - role: "决策者"
      accountable_for: "判断决策"

  # 谁复核
  consulted:
    - role: "复核者"
      accountable_for: "质量把关"

  # 谁升级
  informed:
    - role: "知情人"
      accountable_for: "状态同步"
```
