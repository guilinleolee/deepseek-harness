# MattPocock Improve Codebase Architecture - 架构改进技能

## L0: 一句话描述 (≤15字)
系统性架构改进与术语统一

## L1: 使用场景 (50-100字)
适用于代码库架构混乱、模块职责不清、需要建立通用架构语言或进行大规模重构的场景。通过完整术语体系和系统性分析，提升架构一致性。

## L2: 详细文档

### 核心理念

> "架构是关于模块的接口，而非实现细节。"

### 架构术语体系

| 术语 | 定义 | 示例 |
|------|------|------|
| **深度模块 (Deep Module)** | 小接口，大实现 | `Math.random()` |
| **浅层模块 (Shallow Module)** | 大接口，小实现 | 反面：每个类都有getter/setter |
| **接缝 (Seam)** | 代码中可以介入的点 | 适配器层、依赖注入 |
| **适配器 (Adapter)** | 转换接口的模块 | `V8Adapter`, `NodeAdapter` |
| **特征 (Feature)** | 用户可见的行为 | 搜索、过滤、排序 |
| **机制 (Mechanism)** | 实现特征的内部手段 | 缓存、索引、连接池 |

### 架构分析检查表

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 模块深度检查                                            │
├─────────────────────────────────────────────────────────────┤
│ [ ] 模块是否有小接口、大实现？                              │
│ [ ] 是否避免了浅层模块？                                   │
│ [ ] 模块是否封装了复杂的内部逻辑？                         │
├─────────────────────────────────────────────────────────────┤
│ 2. 接缝识别检查                                            │
├─────────────────────────────────────────────────────────────┤
│ [ ] 变化点是否有清晰的接缝？                               │
│ [ ] 是否使用了适配器模式隔离变化？                         │
│ [ ] 接缝处的依赖是否单向？                                 │
├─────────────────────────────────────────────────────────────┤
│ 3. 特征与机制分离检查                                      │
├─────────────────────────────────────────────────────────────┤
│ [ ] 特征 (Feature) 是否独立于机制？                         │
│ [ ] 机制 (Mechanism) 是否可复用？                          │
│ [ ] 变化是否是特征变化而非机制变化？                       │
├─────────────────────────────────────────────────────────────┤
│ 4. 命名检查                                                │
├─────────────────────────────────────────────────────────────┤
│ [ ] 术语是否在代码库中保持一致？                          │
│ [ ] 术语是否清晰定义了概念边界？                           │
│ [ ] 新术语是否被记录到 CONTEXT.md？                       │
└─────────────────────────────────────────────────────────────┘
```

### 架构改进四步法

```
Step 1: 术语梳理
    │
    ├── 收集现有术语
    ├── 识别不一致
    └── 建立术语表
    │
    ▼
Step 2: 接缝识别
    │
    ├── 找出变化点
    ├── 标记接缝位置
    └── 评估接缝质量
    │
    ▼
Step 3: 深度评估
    │
    ├── 计算模块深度
    ├── 识别浅层模块
    └── 制定改进计划
    │
    ▼
Step 4: 渐进重构
    │
    ├── 从最深模块开始
    ├── 保持接缝完整
    └── 验证行为不变
```

### 模块深度计算

```typescript
// 深度 = 复杂度 / 接口大小

interface DeepModule {
  // 接口小 (1个方法)
  process(data: Input): Promise<Output>;
  // 实现大 (1000行逻辑)
}

interface ShallowModule {
  // 接口大 (10个方法)
  getId(): string;
  setId(id: string): void;
  getName(): string;
  setName(name: string): void;
  // ...
  // 实现小 (几乎没有逻辑)
}
```

### ADR (Architecture Decision Records) 格式

```markdown
# ADR-001: 使用特征目录结构

## 状态
已接受

## 背景
我们需要一种清晰的方式来组织代码，使其与业务特征对齐。

## 决策
我们将对代码组织为特征目录，每个特征包含其所有相关代码。

## 后果
### 正面
- 代码位置清晰
- 特征内聚
- 便于删除特征

### 负面
- 可能需要跨特征共享代码
- 需要建立共享目录规则
```

### CONTEXT.md 格式

```markdown
# 系统上下文

## 核心术语
| 术语 | 定义 | 示例 |
|------|------|------|
| Feature | 用户可见的功能单元 | 搜索、推荐、支付 |
| Mechanism | 底层技术机制 | 缓存、索引 |

## 架构决策
- [ADR-001](./adr/ADR-001.md): 特征目录结构

## 接缝位置
- API层 / 数据层
- 外部服务适配器
```

### 删除测试 (Deletion Test)

评估模块是否应该存在：

```bash
# 问题：如果删除这个模块，会损失多少功能？

Deletion Score:
- 0: 可立即删除，无影响
- 1-3: 删除需要重构
- 4-6: 删除会破坏功能
- 7+: 核心模块，不能删除
```
