# spec-driven-development

## L0: 一句话描述 (≤15字)
规格文档驱动开发，三级边界门控。

## L1: 使用场景 (50-100字)
适用于任何需要从模糊需求转化为可执行代码的场景。当用户提出功能需求时，先输出结构化SPEC规格文档并获得确认，再进行任务拆解和代码实现。核心价值在于强制明确"做什么、不做什么、什么需要确认再做"的三级边界。

## L2: 详细文档

# SPEC-Driven Development (规格驱动开发)

> **核心理念**: "If you don't know where you're going, any road will get you there."
> 每个复杂任务必须先有规格文档，否则不开始代码实现。

## 规格文档格式

每个SPEC必须覆盖以下六大领域：

### 1. Objective (目标)
```markdown
## 目标
- 用户是谁？他们想达成什么？
- 解决的问题是什么？
- 成功的衡量标准是什么？
```

### 2. Commands (命令)
```markdown
## 命令清单
- 用户可执行的命令/操作
- 每个命令的输入和输出
- 命令的优先级和依赖关系
```

### 3. Project Structure (项目结构)
```markdown
## 项目结构
- 目录结构和文件组织
- 模块/组件的职责划分
- 数据流向和接口契约
```

### 4. Code Style (代码风格)
```markdown
## 代码风格
- 命名规范 (PascalCase/camelCase/kebab-case)
- 注释规范 (何时写注释，写什么)
- 格式化规则 (ESLint/Prettier配置)
```

### 5. Testing Strategy (测试策略)
```markdown
## 测试策略
- 测试金字塔 (Unit/Integration/E2E比例)
- 覆盖率目标
- 关键测试用例
```

### 6. Boundaries (边界) — Always/Ask First/Never ⭐核心
```markdown
## 边界定义

### Always Do (必须做)
- 输入验证和边界检查
- 错误处理和日志记录
- 基本的单元测试

### Ask First (需要确认)
- 修改现有API契约
- 变更数据库schema
- 引入新的外部依赖
- 性能影响 >10% 的变更

### Never Do (绝对不做)
- 删除用户数据
- 提交敏感信息到版本控制
- 绕过安全检查
- 硬编码密码或密钥
```

## 四阶段门控工作流

```
┌─────────────────────────────────────────────────────────────┐
│ Phase 1: SPECIFY (规格定义)                                 │
│   输出结构化SPEC文档                                         │
│   ⏸️ 暂停，等待用户确认                                     │
├─────────────────────────────────────────────────────────────┤
│ Phase 2: PLAN (任务规划)                                    │
│   将SPEC拆解为可验证的小任务                                │
│   ⏸️ 暂停，等待用户确认                                     │
├─────────────────────────────────────────────────────────────┤
│ Phase 3: TASKS (任务执行)                                  │
│   按依赖顺序执行任务                                         │
│   ⏸️ 暂停，等待用户确认                                     │
├─────────────────────────────────────────────────────────────┤
│ Phase 4: IMPLEMENT (代码实现)                               │
│   完成任务并验证                                            │
│   ✅ 完成                                                   │
└─────────────────────────────────────────────────────────────┘
```

## 质量门控检查

### SPEC文档质量检查
- [ ] 目标清晰，无歧义
- [ ] 所有命令有明确的输入/输出定义
- [ ] 项目结构符合单一职责原则
- [ ] 代码风格与现有代码库一致
- [ ] 测试策略覆盖核心功能
- [ ] **Boundaries三级明确** (Always/Ask First/Never)
- [ ] 用户确认了SPEC内容

### 任务拆解质量检查
- [ ] 每个任务可独立验证
- [ ] 任务有明确的验收标准
- [ ] 任务有依赖关系和执行顺序
- [ ] 用户确认了任务列表

### 实现质量检查
- [ ] 代码符合SPEC中的命令定义
- [ ] 代码符合SPEC中的项目结构
- [ ] 代码符合SPEC中的代码风格
- [ ] 测试覆盖SPEC中的测试策略
- [ ] 实现未超出SPEC中的Never Do边界

## Rationalizations (反合理化)

| 开发者说 | 真相是 |
|---------|--------|
| "需求很简单，不需要写SPEC" | 简单任务也需要验收标准，否则"完成"定义模糊 |
| "边做边改更快" | 后期重做成本是前期规划的10-100倍 |
| "SPEC会过时，写了也没用" | 过时的SPEC比没有SPEC好，至少知道哪些变了 |
| "用户不知道自己想要什么" | 这恰恰说明需要先探索需求，而不是跳过规格定义 |
| "口头确认就够了" | 口头确认无法追溯，容易产生理解偏差 |

## Red Flags (红旗信号)

⚠️ 用户直接要求开始写代码，不愿意先讨论需求
⚠️ SPEC文档中大量"待定"或"灵活处理"
⚠️ Boundaries部分为空或模糊
⚠️ 没有定义"成功的衡量标准"
⚠️ 项目结构与现有代码库风格严重不一致
⚠️ 任务拆解出现 >500行的单任务

## SDD-CACHE Hook (跨会话HTTP缓存)

用于源码驱动开发阶段的官方文档缓存：

### 工作原理
```
PreToolUse (WebFetch):
  1. 计算URL的sha256作为key
  2. 检查 ~/.claude/sdd-cache/<key>.json 是否存在
  3. 发送HEAD请求验证缓存是否过期
  4. 如果304 Not Modified → 使用缓存内容
  5. 如果有新内容 → 获取并更新缓存

PostToolUse (WebFetch):
  1. 捕获响应内容
  2. 记录validators (最后修改时间、ETag等)
  3. 存储到 ~/.claude/sdd-cache/<key>.json
```

### 启用方式
钩子已集成到 `hooks/sdd-cache-hook.js`，无需额外配置。

### 调试模式
```bash
SDD_CACHE_DEBUG=1 claaude  # 启用调试输出
```
