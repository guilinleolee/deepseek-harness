# OPC 05 MVP设计 (MVP Design)

> 阶段编号: 05
> 阶段类型: 线性阶段
> 核心功能: 设计最小可行产品，明确验证假设和成功标准

## 🎯 L0: 一句话描述

**设计最小可行产品：不做多余功能，只验证核心假设**

## 📋 L1: 使用场景

- 完成商业模式设计后
- 需要验证假设
- 避免过度开发

## 📖 L2: 详细文档

### MVP三阶段模式

```
┌─────────────────────────────────────────────────────────────┐
│  Stage 1: Manual (手工)                                    │
│  - 亲自为每个客户解决问题                                  │
│  - 你就是产品、工程和客服                                  │
│  - 把每一步写下来，成为你的流程                            │
│  - 例：Gumroad在自动化前，Sahil手动发送PayPal付款         │
├─────────────────────────────────────────────────────────────┤
│  Stage 2: Processized (流程化)                            │
│  - 把流程写在纸上，任何人都能做                            │
│  - 如果你休假，别人能接手                                  │
│  - 这就是你的"魔法纸"                                     │
├─────────────────────────────────────────────────────────────┤
│  Stage 3: Productized (产品化)                            │
│  - 现在自动化，让客户自助使用                              │
│  - 只有已经手工验证可行的才自动化                          │
└─────────────────────────────────────────────────────────────┘
```

### MVP vs 传统开发

```
┌─────────────────────────────────────────────────────────────┐
│  传统开发思维                                              │
│  ├── 先做完整产品                                          │
│  ├── 然后找客户                                            │
│  └── 浪费风险: 高                                         │
│                                                             │
│  MVP思维                                                  │
│  ├── 先验证核心假设                                        │
│  ├── 用最小成本测试                                        │
│  └── 浪费风险: 低                                         │
│                                                             │
│  核心问题: 这个MVP验证什么假设？                           │
└─────────────────────────────────────────────────────────────┘
```

### 假设驱动MVP设计

```
┌─────────────────────────────────────────────────────────────┐
│  1. 识别核心假设                                           │
│     从Lean Canvas中选择最重要的3个假设                      │
│                                                             │
│  2. 设计验证实验                                          │
│     ┌─────────────────────────────────────────┐            │
│     │ 假设 → 实验 → 指标 → 结论              │            │
│     │                                     │            │
│     │ 客户有问题 → 访谈10人 → X%有需求 → 继续/转向  │     │
│     │ 愿意付钱   → 收定金   → 3/10付款 → 继续/转向  │     │
│     │ 方案有效   → 用手工   → Y%解决问题 → 继续/转向  │     │
│     └─────────────────────────────────────────┘            │
│                                                             │
│  3. 定义成功标准                                          │
│     - 假设被验证需要什么证据？                            │
│     - 多少客户愿意付费算验证成功？                        │
│     - 验证失败后的转向选项是什么？                       │
└─────────────────────────────────────────────────────────────┘
```

### MVP类型选择

| 类型 | 适用场景 | 成本 | 速度 |
|------|---------|------|------|
| **Wizard of Oz** | 假装有产品，实际人工服务 | 低 | 快 |
| **Concierge** | 亲自服务每个客户 | 中 | 快 |
| **Pitch** | 还没产品，先卖概念 | 低 | 最快 |
| **Landing Page** | 测试需求，先做落地页 | 低 | 快 |
| **Prototyping** | 低保真原型测试 | 低 | 快 |
| **Hybrid** | 部分功能+人工补充 | 中 | 中 |

### MVP设计检查清单

```
□ 核心假设明确
□ 验证实验设计
□ 成功标准定义
□ 失败转向方案
□ 客户接触计划
□ 成本和时间估算
□ 风险识别
□ 验证后下一步
```

## 🚀 命令

```bash
/opc-mvp 开始MVP设计
/opc-mvp 假设 [假设名称] 分析假设验证
/opc-mvp 类型 [类型] 选择MVP类型
/opc-mvp 实验 设计验证实验
/opc-mvp 标准 定义成功标准
```
