# meta-design - 元设计规范技能包

> **版本**: V1.0
> **来源**: 老金元组织方法论 × 天龙引擎V8.96
> **核心**: 定义"最小可治理单元"的5特征 + NAC边界协议

---

## 核心概念

### 什么是"元"？

**元（Meta）** = 复杂系统里最小的可治理单元。

关键不是"最小"，而是**可治理**：
- 能单独进入治理
- 能单独协作
- 能单独替换
- 能单独定位问题

### 5特征判断标准

| 特征 | 问题 | 答不出=不合格 |
|------|------|--------------|
| **独立** | 它单独拿出来，能说清负责什么吗？ | ❌ 不是元 |
| **足够小** | 再往下拆，收益开始变低吗？ | ⚠️ 需判断 |
| **边界清晰** | 它负责什么/不负责什么明确吗？ | ❌ 不是元 |
| **可替换** | 升级/替换它会塌掉整个系统吗？ | ❌ 不成熟 |
| **可复用** | 下次遇到相近任务，它能复用吗？ | ❌ 不成熟 |

### NAC边界协议

**NAC（Negative Attribute Capability）** = 元必须清楚自己不负责什么。

```
┌─────────────────────────────────────────────────────────────┐
│ NAC边界定义模板                                             │
├─────────────────────────────────────────────────────────────┤
│ 负责: [具体职责1, 具体职责2, ...]                           │
│ 不负责: [具体排除1, 具体排除2, ...]                        │
│ 协作边界: [与哪些元协作, 通过什么接口]                      │
│ 隔离边界: [哪些不能直接调用它]                              │
└─────────────────────────────────────────────────────────────┘
```

## 元设计流程

### 5步法

```
Step 1: 任务分析
├── 输入: 复杂任务描述
├── 判断: 复杂度等级（L1简单/L2中等/L3复杂/L4超复杂）
└── 输出: 是否需要元设计

Step 2: 元识别
├── 问题: "这里应该有几个元？"
├── 标准: 每个元是否满足5特征
└── 输出: 元列表（初始）

Step 3: NAC定义
├── 每个元的"负责"清单
├── 每个元的"不负责"清单
├── 协作边界定义
└── 输出: 完整NAC文档

Step 4: 关系建模
├── 元间依赖关系
├── 调用接口定义
├── 数据流转路径
└── 输出: 组织镜像图

Step 5: 治理设计
├── 每个元的校验点
├── 每个元的升级路径
├── 每个元的兜底协议
└── 输出: 治理矩阵
```

### 复杂度等级判断

| 等级 | 特征 | 元数量建议 |
|------|------|-----------|
| **L1** | 单角色、单任务 | 不需要元拆分 |
| **L2** | 多角色、无依赖 | 2-3个元，按职责拆分 |
| **L3** | 多角色、有依赖 | 4-7个元，按流水线拆分 |
| **L4** | 超复杂、多团队 | 7+个元，按组织架构拆分 |

## NAC边界协议模板

```yaml
# meta-nac-template.yaml

meta_id: "元ID"
meta_name: "元名称"

nac:
  responsible_for:
    - "职责1：具体描述"
    - "职责2：具体描述"
    - "职责3：具体描述"

  not_responsible_for:
    - "排除1：具体描述"
    - "排除2：具体描述"

  collaboration_boundary:
    depends_on:
      - "依赖元A：通过接口X"
      - "依赖元B：通过接口Y"
    provides_to:
      - "向元C提供：输出X"
      - "向元D提供：输出Y"
    isolation_rules:
      - "不能直接调用：元E（需通过元F中转）"
      - "不能访问：共享状态X"

  entry_criteria:
    - "激活条件1"
    - "激活条件2"

  exit_criteria:
    - "完成条件1"
    - "完成条件2"

  error_boundary:
    - "本元处理：类型A错误"
    - "上报给：元X（类型B/C错误）"
```

## 元间接口协议

### 接口定义标准

```yaml
interfaces:
  input:
    - name: "接口名"
      type: "数据类型"
      required: true/false
      source: "来源元"

  output:
    - name: "接口名"
      type: "数据类型"
      destination: "目标元"

  error:
    - type: "错误类型"
      handled_by: "处理元"
      escalation_to: "升级元"
```

### 调用关系建模

```
元A ──调用──▶ 元B
    │
    ├── 接口: output_A_to_B
    ├── 条件: [前置条件]
    ├── 时机: [何时调用]
    └── 异常: [异常处理]
```

## 治理设计

### 校验点设计

```yaml
checkpoints:
  - id: "cp-1"
    meta: "元A"
    when: "执行前"
    check: "前置条件验证"
    on_fail: "skip/rollback/notify"

  - id: "cp-2"
    meta: "元A"
    when: "执行后"
    check: "输出质量验证"
    on_fail: "rollback/retry/escalate"
```

### 升级路径设计

```yaml
escalation:
  - level: 1
    trigger: "局部失败"
    handler: "本元自愈"

  - level: 2
    trigger: "跨元依赖失败"
    handler: "编排协调元"

  - level: 3
    trigger: "系统性失败"
    handler: "元审查师"
```

### 兜底协议

```yaml
fallback:
  - scenario: "场景描述"
    condition: "触发条件"
    action: "兜底动作"
    recovery: "恢复步骤"
```

## 命令速查

```bash
# 元设计分析
/meta-design <任务>                 # 元设计咨询
/meta-design --complexity <任务>   # 复杂度评估

/nac-template <元ID>               # 生成NAC模板
/nac-define <元ID> --responsible "负责1" --not-responsible "不负责1"

# 元关系建模
/meta-graph <系统>                   # 生成元关系图

# 治理设计
/governance-design <元>            # 治理矩阵设计
/checkpoint-add <元> --when "执行后" --check "验证项"
```
