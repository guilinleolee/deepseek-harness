# NAC边界定义提示词模板 - 负面能力引导框架

> **版本**: V1.0
> **来源**: 天龙引擎V9.02 × 老金元组织方法论
> **用途**: 引导用户完成一个"元"的NAC边界定义

---

## NAC边界定义引导流程

```
┌─────────────────────────────────────────────────────────────┐
│ NAC边界定义5步法                                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ Step 1: 理解NAC vs DAC                                    │
│    → DAC = 这个元能做什么？（正面能力）                    │
│    → NAC = 这个元不做什么？（负面能力）                      │
│                                                             │
│ Step 2: 识别五大边界类型                                    │
│    → 领域边界、能力边界、规模边界、质量边界、安全边界        │
│                                                             │
│ Step 3: 逐项定义NAC                                        │
│    → 每项说明：具体排除事项 + 原因 + 应该由谁处理           │
│                                                             │
│ Step 4: 设计违反检测                                        │
│    → 如何识别NAC被违反？                                   │
│    → 违反后如何响应？                                       │
│                                                             │
│ Step 5: 编写NAC边界文档                                    │
│    → 用清晰的语言描述边界                                   │
│    → 让协作者一目了然                                       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## Step 1: DAC vs NAC 理解

### 引导对比

```
┌─────────────────────────────────────────────────────────────┐
│ DAC vs NAC - 一体两面                                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  DAC（正面能力）                                           │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ 这个元能做什么？                                      │   │
│  │ 用"能够"造句：                                       │   │
│  │ → 能够解析JSON格式数据                               │   │
│  │ → 能够调用内部API接口                                │   │
│  │ → 能够处理1000条以内的数据                           │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  NAC（负面能力）                                           │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ 这个元不做什么？                                       │   │
│  │ 用"不能"造句：                                       │   │
│  │ → 不能处理XML格式数据（应该用专门的XML解析元）        │   │
│  │ → 不能直接访问外部互联网（应该通过网关元）            │   │
│  │ → 不能处理超过1000条的数据（应该分批或升级）        │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  原则：NAC边界 = DAC的补集                                │
│  明确NAC = 明确DAC的边界                                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## Step 2: 五大边界类型

### 边界类型概览

```
┌─────────────────────────────────────────────────────────────┐
│ NAC边界类型矩阵                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ ┌─────────────┬─────────────────────────────────────────┐ │
│ │ 边界类型   │ 核心问题                                 │ │
│ ├─────────────┼─────────────────────────────────────────┤ │
│ │ 领域边界   │ 这个任务在我的专业领域内吗？              │ │
│ ├─────────────┼─────────────────────────────────────────┤ │
│ │ 能力边界   │ 我有足够的知识/能力处理这个任务吗？       │ │
│ ├─────────────┼─────────────────────────────────────────┤ │
│ │ 规模边界   │ 任务规模在我的处理能力范围内吗？          │ │
│ ├─────────────┼─────────────────────────────────────────┤ │
│ │ 质量边界   │ 我能达到任务要求的最低质量标准吗？        │ │
│ ├─────────────┼─────────────────────────────────────────┤ │
│ │ 安全边界   │ 我有权限访问任务所需的数据/系统吗？       │ │
│ └─────────────┴─────────────────────────────────────────┘ │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 每种边界的引导问题

#### 1. 领域边界

```
┌─────────────────────────────────────────────────────────────┐
│ 领域边界 - 专业分工                                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 引导问题：                                                  │
│ 1. 这个元的核心专业领域是什么？                            │
│    → 列举2-3个核心领域                                     │
│                                                             │
│ 2. 哪些领域明确不属于这个元？                              │
│    → 列举至少3个排除领域                                   │
│                                                             │
│ 3. 排除领域的任务应该交给谁处理？                           │
│    → 每个排除领域指明处理者                                 │
│                                                             │
│ 示例：                                                      │
│ 元：数据解析元                                             │
│ 负责：JSON解析、数据验证、格式转换                          │
│ 不负责：                                                    │
│   - XML解析（应该由XML解析元处理）                         │
│   - 业务逻辑处理（应该由业务元处理）                       │
│   - 数据存储（应该由存储元处理）                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 2. 能力边界

```
┌─────────────────────────────────────────────────────────────┐
│ 能力边界 - 知识与技能                                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 引导问题：                                                  │
│ 1. 这个元具备哪些核心能力？                                 │
│    → 列举核心能力清单                                      │
│                                                             │
│ 2. 哪些能力是这个元不具备的？                              │
│    → 列举能力缺口                                          │
│                                                             │
│ 3. 能力缺口的任务如何处理？                                │
│    → 升级到更高层级？                                       │
│    → 委托给其他元？                                         │
│    → 拒绝并说明原因？                                       │
│                                                             │
│ 示例：                                                      │
│ 元：翻译元                                                 │
│ 能处理：英→中、中→英、通用领域文本                        │
│ 不能处理：                                                  │
│   - 专业知识翻译（医学/法律→应该用专业翻译元）            │
│   - 实时口语翻译（→应该用语音翻译元）                      │
│   - 超过10000字的翻译（→应该分批处理）                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 3. 规模边界

```
┌─────────────────────────────────────────────────────────────┐
│ 规模边界 - 处理能力上限                                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 引导问题：                                                  │
│ 1. 这个元能处理的规模上限是多少？                          │
│    → 数据量上限：___                                      │
│    → 并发数上限：___                                      │
│    → 单次任务耗时上限：___                                 │
│    → 内存使用上限：___                                    │
│                                                             │
│ 2. 超出规模时如何处理？                                    │
│    → 分批处理？                                            │
│    → 升级到有更大处理能力的元？                             │
│    → 直接拒绝并建议用户拆分任务？                           │
│                                                             │
│ 示例：                                                      │
│ 元：数据处理元                                             │
│ 规模上限：                                                  │
│   - 单次处理数据量：≤1000条                               │
│   - 单次任务耗时：≤10秒                                   │
│   - 最大并发数：≤10                                       │
│ 超限处理：                                                  │
│   - >1000条 → 建议分批或使用批处理元                      │
│   - >10秒 → 触发超时升级                                   │
│   - >10并发 → 触发限流                                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 4. 质量边界

```
┌─────────────────────────────────────────────────────────────┐
│ 质量边界 - 质量标准                                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 引导问题：                                                  │
│ 1. 这个元能保证的最低质量标准是什么？                      │
│    → 准确率：___%                                         │
│    → 可用性：___%                                         │
│    → 响应时间：___                                        │
│                                                             │
│ 2. 哪些质量要求是这个元无法达到的？                        │
│    → 列举质量缺口                                         │
│                                                             │
│ 3. 无法达到质量要求时如何处理？                            │
│    → 明确告知用户质量限制                                   │
│    → 提供降级方案？                                        │
│    → 升级到更高质量保障的元？                              │
│                                                             │
│ 示例：                                                      │
│ 元：AI生成元                                               │
│ 质量承诺：                                                  │
│   - 准确率：≥95%（常规任务）                              │
│   - 可用性：99.9%                                         │
│ 质量限制：                                                  │
│   - 100%准确率无法保证（需要人工复核）                    │
│   - 7x24无间断无法保证（需要高可用架构）                  │
│   - 零错误无法保证（需要完整容错机制）                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 5. 安全边界

```
┌─────────────────────────────────────────────────────────────┐
│ 安全边界 - 权限与访问控制                                   │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 引导问题：                                                  │
│ 1. 这个元可以访问哪些数据/系统？                          │
│    → 列举授权范围                                         │
│                                                             │
│ 2. 这个元不能访问哪些数据/系统？                          │
│    → 列举禁止范围                                         │
│                                                             │
│ 3. 越界访问如何处理？                                     │
│    → 直接拒绝                                              │
│    → 触发安全告警？                                       │
│    → 请求授权后重试？                                      │
│                                                             │
│ 示例：                                                      │
│ 元：数据处理元                                             │
│ 可访问：                                                    │
│   - 内部API                                               │
│   - 授权数据源                                            │
│   - 安全日志                                              │
│ 禁止访问：                                                  │
│   - 外部互联网（需要通过网关）                            │
│   - 敏感PII数据（需要脱敏处理）                           │
│   - 系统配置（需要管理员权限）                             │

│                                                             │
```

## Step 3: NAC边界决策矩阵

### 决策矩阵模板

```yaml
boundary_decisions:
  - boundary: "数据处理"
    can: ["解析", "转换", "验证", "存储"]
    cannot: ["实时流处理", "跨租户访问", "无限数据量"]
    escalation: "编排元"

  - boundary: "API调用"
    can: ["内部服务", "授权外部API", "重试机制"]
    cannot: ["无认证外部API", "无限调用频率", "敏感信息明文传输"]
    escalation: "网关元"

  - boundary: "用户交互"
    can: ["信息展示", "简单确认", "状态反馈"]
    cannot: ["复杂表单处理", "多步骤引导", "实时双向通信"]
    escalation: "前端元"

  - boundary: "错误处理"
    can: ["已知错误恢复", "重试机制", "优雅降级"]
    cannot: ["未知错误诊断", "系统级修复", "数据恢复"]
    escalation: "运维元"
```

## Step 4: NAC违反检测

### 违反检测设计

```
┌─────────────────────────────────────────────────────────────┐
│ NAC违反检测机制                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 【检测模式】                                                 │
│                                                             │
│ 1. 范围蔓延                                                │
│    指标：元开始处理原本不负责的领域                        │
│    检测：监控NAC边界任务占比                                │
│    阈值：NAC相关任务占比>30% → 触发告警                  │
│                                                             │
│ 2. 能力超载                                                │
│    指标：尝试处理无法胜任的任务                            │
│    检测：错误率上升、延迟增加                               │
│    阈值：错误率>5%或延迟>P99 → 触发升级                  │
│                                                             │
│ 3. 边界模糊                                                 │
│    指标：职责重叠或真空地带                                │
│    检测：跨元依赖复杂度上升                                 │
│    阈值：依赖数>10 → 触发边界审查                        │
│                                                             │
│ 【响应机制】                                                 │
│                                                             │
│ 1. 自动检测：启用                                         │
│ 2. 自动升级：启用                                          │
│ 3. 升级目标：编排元 / 治理元                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 检测指标定义

```yaml
violation_detection:
  patterns:
    - name: "范围蔓延"
      indicator: "元开始处理原本不负责的领域"
      detection_method: "监控NAC边界任务占比"
      threshold: ">30%"
      action: "notify"

    - name: "能力超载"
      indicator: "尝试处理无法胜任的任务"
      detection_method: "错误率上升、延迟增加"
      threshold: "错误率>5%或延迟>P99"
      action: "escalate"

    - name: "边界模糊"
      indicator: "职责重叠或真空地带"
      detection_method: "跨元依赖复杂度上升"
      threshold: "依赖数>10"
      action: "review"

  responses:
    auto_detect: true
    auto_escalate: true
    escalation_target: "编排元/治理元"
```

## Step 5: NAC边界文档模板

### 文档结构

```
┌─────────────────────────────────────────────────────────────┐
│ NAC边界文档模板                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ ## 元概述                                                   │
│ [元名称] 负责 [核心职责]，其边界定义如下：                  │
│                                                             │
│ ## 明确不负责                                               │
│ 1. **领域A**：原因 + 应该由谁处理                          │
│ 2. **领域B**：原因 + 应该由谁处理                          │
│ 3. **领域C**：原因 + 应该由谁处理                          │
│                                                             │
│ ## 边界触发条件                                            │
│ 当遇到以下情况时，应触发NAC边界检查：                       │
│ - 任务涉及多个领域                                          │
│ - 任务超出规模限制                                          │
│ - 任务需要跨元协作                                          │
│                                                             │
│ ## 边界处理流程                                            │
│ 1. 识别是否在NAC范围内                                     │
│ 2. 如果超出边界，评估是否可以拆分                          │
│ 3. 如果无法拆分，升级到编排元                              │
│ 4. 如果可以拆分，委托给相应元处理                          │
│                                                             │
│ ## 违反检测指标                                            │
│ - 范围蔓延：NAC任务占比>30%                               │
│ - 能力超载：错误率>5%或延迟>P99                           │
│ - 边界模糊：依赖数>10                                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```
