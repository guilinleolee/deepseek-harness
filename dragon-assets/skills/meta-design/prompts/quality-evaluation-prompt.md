# 元5特征评估提示词模板 - 质量评估引导框架

> **版本**: V1.0
> **来源**: 天龙引擎V9.02 × 老金元组织方法论
> **用途**: 引导用户完成一个"元"的5特征质量评估

## 5特征评估概览

```
┌─────────────────────────────────────────────────────────────┐
│ 元5特征评估体系                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌────────────┐                                           │
│  │   独立    │ → 单独拿出来能说清负责什么？               │
│  └─────┬──────┘                                           │
│        ↓                                                  │
│  ┌────────────┐                                           │
│  │  足够小   │ → 再往下拆，收益开始变低？                  │
│  └─────┬──────┘                                           │
│        ↓                                                  │
│  ┌────────────┐                                           │
│  │  边界清晰  │ → 负责什么/不负责什么明确？                │
│  └─────┬──────┘                                           │
│        ↓                                                  │
│  ┌────────────┐                                           │
│  │  可替换    │ → 升级/替换会塌掉系统吗？                  │
│  └─────┬──────┘                                           │
│        ↓                                                  │
│  ┌────────────┐                                           │
│  │  可复用    │ → 下次遇到相近任务能复用？                  │
│  └────────────┘                                           │
│                                                             │
│  综合评分 = Σ(各特征得分) / 25 × 100%                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 特征1：独立评估

### 引导问题

```
┌─────────────────────────────────────────────────────────────┐
│ 独立评估 - 灵魂三问                                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 1. 这个元能独立完成什么？                                   │
│    → 列出它的核心输出                                      │
│    → 这些输出在没有其他元的情况下能产生吗？                 │
│                                                             │
│ 2. 这个元的输入和输出是什么？                              │
│    → 输入：___                                            │
│    → 输出：___                                            │
│    → 输入是否可以从外部直接获取，还是必须依赖其他元？       │
│                                                             │
│ 3. 这个元不依赖其他元能工作吗？                            │
│    → 如果必须依赖其他元，这些依赖是什么？                   │
│    → 依赖程度如何？（强依赖/弱依赖/可选依赖）              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 评分标准

| 得分 | 等级 | 描述 |
|------|------|------|
| 1分 | 无法独立 | 必须依赖多个其他元，缺少任何一个都无法工作 |
| 2分 | 高度依赖 | 依赖2-3个其他元，少一个就有问题 |
| 3分 | 中度依赖 | 依赖1-2个其他元，但有降级方案 |
| 4分 | 基本独立 | 核心功能可独立，辅助功能需要少量依赖 |
| 5分 | 完全独立 | 自身功能完整，依赖仅用于增强而非必需 |

### 示例

```
元：用户认证元
评估：
  - 核心功能（密码验证）可独立完成 → 4分
  - 但发送验证码需要短信元，第三方登录需要OAuth元 → 降为3分
结论：基本独立，有中度依赖
```

## 特征2：足够小评估

### 引导问题

```
┌─────────────────────────────────────────────────────────────┐
│ 足够小评估 - 灵魂三问                                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 1. 当前这个元承担了多少职责？                               │
│    → 列出所有职责清单                                      │
│    → 数量：___个                                          │
│                                                             │
│ 2. 如果再往下拆，收益会变低吗？                             │
│    → 拆分后，每个子元的职责会过于简单吗？                   │
│    → 拆分后，协作成本会超过收益吗？                         │
│    → 如果是 → 当前粒度刚好                                  │
│    → 如果否 → 考虑进一步拆分                                │
│                                                             │
│ 3. 什么情况下应该拆？什么情况下应该合？                     │
│    → 拆分的条件：___                                      │
│    → 合并的条件：___                                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 评分标准

| 得分 | 等级 | 描述 |
|------|------|------|
| 1分 | 过于臃肿 | 职责数量>10个，难以理解和维护 |
| 2分 | 偏大 | 职责数量7-10个，建议拆分 |
| 3分 | 合理偏大 | 职责数量5-7个，可接受 |
| 4分 | 理想大小 | 职责数量3-5个，粒度合适 |
| 5分 | 过于细小 | 职责数量≤2个，可能粒度过细 |

### 拆分决策树

```
┌─────────────────────────────────────────────────────────────┐
│ 拆分决策树                                                 │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 职责数量 > 7 ?                                            │
│   ├─ 是 → 考虑拆分                                        │
│   │         ↓                                              │
│   │      有明显独立的子领域？                               │
│   │         ├─ 是 → 按子领域拆分                           │
│   │         └─ 否 → 检查是否可合并到其他元                │
│   │                                                         │
│   └─ 否 → 职责数量 < 3 ?                                 │
│               ├─ 是 → 检查是否可合并到相关元               │
│               └─ 否 → 当前粒度合适                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 特征3：边界清晰评估

### 引导问题

```
┌─────────────────────────────────────────────────────────────┐
│ 边界清晰评估 - 灵魂三问                                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 1. 这个元负责什么？                                          │
│    → 列出3-5个明确负责的事项                                │
│    → 每项能一句话说清楚吗？                                 │
│                                                             │
│ 2. 这个元不负责什么？                                       │
│    → 列出2-3个明确不负责的事项                              │
│    → 每项有明确说明"应该由谁处理"吗？                       │
│                                                             │
│ 3. 边界模糊的区域在哪里？                                    │
│    → 列出可能存在灰色地带的地方                             │
│    → 这些灰色地带可能导致什么问题？                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 评分标准

| 得分 | 等级 | 描述 |
|------|------|------|
| 1分 | 边界模糊 | 无法清晰描述负责和不负责的边界 |
| 2分 | 部分清晰 | 知道大概边界，但无法清晰描述 |
| 3分 | 基本清晰 | 有明确的内外边界，但灰色地带较多 |
| 4分 | 清晰 | 边界清晰，灰色地带少 |
| 5分 | 非常清晰 | 边界非常清晰，NAC文档完整，协作者一目了然 |

### 边界清晰度检查

```
┌─────────────────────────────────────────────────────────────┐
│ 边界清晰度检查清单                                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ □ 能用一句话描述核心职责                                     │
│ □ 职责清单≤7项                                             │
│ □ 每项职责有明确的输入输出                                   │
│ □ 有完整的NAC边界定义                                       │
│ □ 灰色地带已识别并有处理建议                                 │
│ □ 协作者能通过文档理解边界                                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 特征4：可替换评估

### 引导问题

```
┌─────────────────────────────────────────────────────────────┐
│ 可替换评估 - 灵魂三问                                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 1. 有多少元依赖这个元？                                     │
│    → 列出所有下游依赖方                                    │
│    → 数量：___个                                          │
│                                                             │
│ 2. 有多少系统直接调用这个元？                               │
│    → 列出所有直接调用方                                    │
│    → 数量：___个                                          │
│                                                             │
│ 3. 替换这个元的影响范围有多大？                            │
│    → 低影响：替换不需要通知任何人                           │
│    → 中影响：替换需要通知调用方，但接口兼容                 │
│    → 高影响：替换需要协调多个团队，接口可能不兼容            │
│    → 极高影响：替换会破坏系统，必须完整重建                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 评分标准

| 得分 | 等级 | 描述 |
|------|------|------|
| 1分 | 不可替换 | 替换=系统崩溃，必须完整重建 |
| 2分 | 难替换 | 替换需要协调>5个团队，接口强耦合 |
| 3分 | 中等可替换 | 替换需要通知调用方，但有标准接口 |
| 4分 | 较易替换 | 替换只需通知少量调用方，接口兼容 |
| 5分 | 随时可替换 | 替换无影响，接口完全解耦 |

### 版本策略

```yaml
replaceability:
  version_strategy:
    strategy: "滚动/蓝绿/并行"
    description:
      滚动: "逐步替换，逐个节点切换"
      蓝绿: "新旧并行，流量切换"
      并行: "新旧同时运行，逐步切流"

  backward_compatible:
    required: true
    compatibility_period: "至少保持3个月"

  replacement_impact:
    low:
      description: "替换影响小，可独立升级"
      actions: ["通知相关方", "监控新版本稳定性"]

    medium:
      description: "替换需要协调多个元"
      actions: ["提前通知", "制定切换计划", "回滚方案"]

    high:
      description: "替换会破坏系统"
      actions: ["禁止直接替换", "必须完整重建", "先建后拆"]
```

## 特征5：可复用评估

### 引导问题

```
┌─────────────────────────────────────────────────────────────┐
│ 可复用评估 - 灵魂三问                                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 1. 这个元的历史复用情况如何？                               │
│    → 在哪些项目中被复用？                                   │
│    → 复用效果如何？                                         │
│                                                             │
│ 2. 接口标准化了吗？                                         │
│    → 输入输出接口是否规范？                                 │

│    → 文档是否完整？                                         │
│                                                             │
│ 3. 抽象程度如何？                                           │
│    → 是否绑定了特定业务逻辑？                               │
│    → 是否可以跨项目使用？                                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 评分标准

| 得分 | 等级 | 描述 |
|------|------|------|
| 1分 | 不可复用 | 强耦合特定项目，无法提取 |
| 2分 | 难复用 | 接口不标准，文档缺失 |
| 3分 | 基本可复用 | 接口基本标准，但需要适配 |
| 4分 | 较易复用 | 接口标准，文档完整，稍作适配即可 |
| 5分 | 完全可复用 | 接口标准化，文档完整，开箱即用 |

## 综合评分

### 评分汇总表

```yaml
quality_score:
  independence: ___/5
  granularity: ___/5
  boundaries: ___/5
  replaceability: ___/5
  reusability: ___/5

  total: ___/25
  percentage: ___%

  qualification:
    excellent: "≥20分（80%）"
    good: "15-19分（60-79%）"
    pass: "12-14分（48-59%）"
    fail: "<12分（<48%）"
```

### 通过标准

| 等级 | 分数 | 含义 | 行动 |
|------|------|------|------|
| **优秀** | ≥20/25 | 五特征都表现良好 | 通过，可进入设计阶段 |
| **良好** | 15-19/25 | 大部分特征合格，有改进空间 | 通过，但需列出改进项 |
| **及格** | 12-14/25 | 基本合格，需要改进 | 有条件通过，明确改进计划 |
| **不及格** | <12/25 | 存在重大缺陷 | 不通过，需重新设计 |

### 改进优先级

```
┌─────────────────────────────────────────────────────────────┐
│ 改进优先级矩阵                                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 高优先级（必须改进）                                         │
│ ├─ 边界清晰度 < 3分 → 必须明确定义边界                      │
│ ├─ 可替换性 < 2分 → 必须解耦接口                          │
│ └─ 独立性 < 2分 → 必须降低依赖                            │
│                                                             │
│ 中优先级（建议改进）                                         │
│ ├─ 粒度不合理 → 考虑拆分或合并                             │
│ └─ 可复用性 < 3分 → 标准化接口                             │
│                                                             │
│ 低优先级（可选改进）                                         │
│ └─ 历史复用率低 → 积累复用案例                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```
