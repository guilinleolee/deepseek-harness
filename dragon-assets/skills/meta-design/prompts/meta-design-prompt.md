## Step 1: 元身份定义

### 引导问题

```
┌─────────────────────────────────────────────────────────────┐
│ 元身份定义 - 灵魂三问                                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 1. 这个元叫什么？                                          │
│    (meta_name)                                            │
│    → 名称应该简洁、明确、见名知意                           │
│                                                             │
│ 2. 这个元的核心职责是什么？                                 │
│    (core_responsibility)                                   │
│    → 用一句话描述：它负责什么？                             │
│    → 如果这句话超过20个字，说明职责不够聚焦                 │
│                                                             │
│ 3. 这个元解决什么问题？                                     │
│    (problem_solved)                                       │
│    → 它为什么存在？它的不可替代性是什么？                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 输出模板

```yaml
meta_identity:
  name: "元名称"
  alias: ["别名1", "别名2"]
  core_responsibility: "一句话核心职责（≤20字）"
  problem_solved: "解决的问题描述"
  value_proposition: "价值主张：相比其他方案，它的优势是什么？"
```

## Step 2: 5特征评估

### 引导问题

```
┌─────────────────────────────────────────────────────────────┐
│ 5特征评估 - 每个特征的灵魂拷问                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 【独立】这个元能单独拿出来说清楚吗？                         │
│    → 如果没有上下文，你能用一句话描述它的职责吗？             │
│    → 它依赖其他元才能工作吗？                               │
│                                                             │
│ 【足够小】这个元再往下拆，收益开始变低吗？                   │
│    → 当前职责数量：___个                                    │
│    → 如果>7个，考虑拆分                                     │
│    → 如果<3个，考虑合并                                     │
│                                                             │
│ 【边界清晰】这个元的边界在哪里？                             │
│    → 列出3-5个它负责的具体事项                             │
│    → 列出2-3个它明确不负责的事项                           │
│                                                             │
│ 【可替换】升级或替换它会塌掉整个系统吗？                     │
│    → 有多少元依赖它？                                       │
│    → 有多少系统直接调用它？                                 │
│                                                             │
│ 【可复用】下次遇到相近任务，它能复用吗？                     │
│    → 接口标准化了吗？                                       │
│    → 有没有抽象到可以跨项目使用？                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 评分标准

| 特征 | 1分 | 2分 | 3分 | 4分 | 5分 |
|------|------|------|------|------|------|
| **独立** | 无法独立 | 需要大量上下文 | 需要部分上下文 | 基本可独立 | 完全可独立 |
| **足够小** | 职责>10个 | 职责7-10个 | 职责5-7个 | 职责3-5个 | 职责≤3个 |
| **边界清晰** | 边界模糊 | 边界部分清晰 | 边界基本清晰 | 边界清晰 | 边界非常清晰 |
| **可替换** | 替换=系统崩溃 | 替换需大量协调 | 替换需协调 | 替换需通知 | 替换无影响 |
| **可复用** | 强耦合无法复用 | 接口不标准 | 基本可复用 | 较易复用 | 完全可复用 |

### 通过标准

- 总分 ≥ 20/25 → 优秀，通过
- 总分 15-19/25 → 良好，需改进
- 总分 < 15/25 → 不及格，需重构

## Step 3: NAC边界定义

### 引导问题

```
┌─────────────────────────────────────────────────────────────┐
│ NAC边界定义 - 灵魂三问                                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 1. 这个元不做什么？                                         │
│    → 列出至少3个它明确不负责的事项                           │
│    → 每项说明原因，以及"应该由谁处理"                       │
│                                                             │
│ 2. 超出边界时怎么办？                                       │
│    → 识别到超出边界 → 评估是否可以拆分                      │
│    → 如果无法拆分 → 升级到编排元                            │
│    → 如果可以拆分 → 委托给相应元处理                         │
│                                                             │
│ 3. 边界触发条件是什么？                                     │
│    → 什么情况下应该触发NAC边界检查？                        │
│    → 任务涉及多个领域？超出规模限制？需要跨元协作？          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### NAC边界类型

```yaml
nac_types:
  domain:
    description: "领域边界"
    questions:
      - "这个任务在我的专业领域内吗？"
      - "这个任务应该由哪个专业领域的元处理？"

  capability:
    description: "能力边界"
    questions:
      - "我有足够的知识/能力处理这个任务吗？"
      - "这个任务需要什么特殊能力？"

  scale:
    description: "规模边界"
    questions:
      - "任务规模在我的处理能力范围内吗？"
      - "如果超出，处理上限是多少？"

  quality:
    description: "质量边界"
    questions:
      - "我能达到任务要求的最低质量标准吗？"
      - "需要什么额外的质量保障措施？"

  security:
    description: "安全边界"
    questions:
      - "我有权限访问任务所需的数据/系统吗？"
      - "任务涉及敏感信息吗？"
```

## Step 4: 接口契约设计

### 引导问题

```
┌─────────────────────────────────────────────────────────────┐
│ 接口契约设计 - 契约三问                                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 1. 它需要什么输入？                                         │
│    → 列出所有必要的输入参数                                 │
│    → 每个参数：名称、类型、是否必填、默认值、验证规则       │
│    → 最大参数数量限制：___个（建议≤10个）                  │
│                                                             │
│ 2. 它产生什么输出？                                         │
│    → 列出所有可能的输出类型                                 │
│    → success / partial / failed 三种状态                     │
│    → metadata：timestamp、request_id、processing_time         │
│                                                             │
│ 3. 它依赖哪些元？被哪些元依赖？                             │
│    → 上游依赖：列出所有输入来源元                           │
│    → 下游依赖：列出所有输出去向元                           │
│    → 依赖关系是否形成循环？（循环依赖是大忌）                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 接口设计检查

```
┌─────────────────────────────────────────────────────────────┐
│ 接口设计检查清单                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ □ 参数数量 ≤ 10个                                           │
│ □ 所有参数都有类型定义                                      │
│ □ 所有必填参数都有验证规则                                  │
│ □ 错误码覆盖所有可能的失败场景                              │
│ □ 超时时间在合理范围内（建议≤30s）                         │
│ □ 接口变更向后兼容                                          │
│ □ 有完整的使用文档和示例                                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```
