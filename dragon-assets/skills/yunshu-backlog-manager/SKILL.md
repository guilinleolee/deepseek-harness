# yunshu-backlog-manager

> 来源: [yunshu0909/yunshu_skillshub](https://github.com/yunshu0909/yunshu_skillshub) backlog-manager, 痛点驱动6步闭环需求池管理

## 核心原则

- **痛点驱动** — 只收集真实痛点和明确想法，不做假设性规划
- **AI整理，用户决策** — AI负责追问、归类、合并；用户负责确认和拍板
- **先归档，再说做不做** — 新想法先进池子，不急着排优先级或启动开发
- **池子要活** — 定期清理过时条目，升档想清楚的条目
- **不越界** — 需求池管理到"可以做了"为止，后续设计/PRD/开发由其他流程接管

## 四状态分类

| 状态 | 说明 | 必填字段 |
|------|------|---------|
| **可以做了** | 痛点清晰，知道要做成什么样，随时能进设计/PRD | 痛点、方案 |
| **需要想想** | 方向有了，细节没展开，需要调研或讨论 | 方向 |
| **先放着** | 记着就行，现在不花精力想 | 想法 |
| **已完成** | 做完了，标版本号归档 | 完成时间、简述 |

## 6步工作流

### 第1步：收集 — 用户抛出新想法

主动追问三件事：
- **痛点是什么** — 现在遇到了什么问题？什么场景下不爽？
- **频率多高** — 多久碰到一次？
- **现在怎么绕** — 不做这个功能的话，手动怎么解决？

整理成一句话描述，向用户确认。

**禁止**：用户说一句话就直接写进需求池，必须先追问确认。

### 第2步：归类 — 判断状态和合并

1. 读取现有需求池，检查是否可合并
2. 判断状态：能说清痛点和方案→**可以做了**；有方向但细节模糊→**需要想想**；用户说"先记着"→**先放着**
3. 向用户确认归类结果，用户同意后再写入文件

**禁止**：AI自行判断状态不跟用户确认；强行合并用户认为不同的需求。

### 第3步：写入 — 更新需求池文件

位置：`docs/需求池.md`
1. 在对应分区添加条目详情
2. 更新总览表（加新行或修改已有行）
3. 如果发生合并，更新被合并条目

### 第4步：整理 — 定期过一遍池子

当用户说"整理一下需求池"或"看看需求池"时：
1. 逐条过，给出建议（过时→删除；想清楚了→升档；模糊→追问）
2. 没变化的直接跳过，不废话
3. 用户逐条确认后，批量更新文件

**禁止**：没有用户确认就批量修改状态。

### 第5步：筛选 — 挑下一个版本做什么

当用户说"下一个版本做什么"或"挑一个来做"时：
1. 列出所有"可以做了"的条目
2. 如果为空，从"需要想想"里挑最接近的，帮用户聊清楚
3. 用三标准分析：
   - **频率**：你多久被这个问题卡一次？
   - **可绕过性**：不做的话手动能搞定吗？多麻烦？
   - **ROI**：做完之后日常能省多少事？
4. 给出分析结果，**不替用户做决定**，让用户选

### 第6步：归档 — 版本完成

当用户说"xxx做完了"或"标记完成"时：
1. 将条目从当前分区移到"已完成"
2. 补充版本号和完成时间
3. 更新总览表状态
4. 检查依赖条目是否可以升档，提醒用户

## 三标准筛选（必问用户）

| 标准 | 问题 |
|------|------|
| 频率 | 你多久被这个问题卡一次？ |
| 可绕过性 | 不做的话手动能搞定吗？多麻烦？ |
| ROI | 做完之后日常能省多少事？ |

## AI绝不应该做的

- 替用户决定做哪个需求
- 用户扔了一个想法就开始做设计或写PRD
- 自己编造需求内容
- 没有用户确认就修改需求池文件
- 给所有条目强行排优先级
- 把需求池当待办清单催用户

## 需求池文件模板

```markdown
# 需求池

> 随手记，随时加，隔段时间过一遍。
>
> 状态说明：
> - **可以做了** — 痛点清晰，知道要做成什么样，随时能进设计/PRD
> - **需要想想** — 方向有了，细节没展开，需要调研或讨论
> - **先放着** — 记着就行，现在不花精力想
> - **已完成** — 做完了，标版本号归档

---

## 总览

| # | 需求 | 状态 | 依赖 | 备注 |
|---|------|------|------|------|
| 1 | xxx | 可以做了 | 无 | xxx |

---

### 需求名称
- 痛点：xxx
- 方案：xxx
- 备注：xxx

## 需要想想
```

## 与50-01产品策划集成

当50-01产品策划收到需求收集请求时，自动切换到此工作流模式，负责：
- 用户随时抛出的想法/痛点 → 追问 → 整理 → 归类 → 入池
- 用户要求整理 → 定期过池子
- 用户要求筛选 → 三标准分析候选
- 用户说完成 → 版本归档

需求池流程到"可以做了"为止，后续设计/PRD由 `/prd-doc-writer` 或 `/design-exploration` 接管。
