# 08发布师 Learned Patterns

## 📅 最后更新: 2026-04-18

---

## ✅ Effective Patterns (有效模式)

### Pattern 1: 小规模灰度发布
**发现场景**: 全量发布出问题，回滚影响大
**做法**: 先1%→5%→10%→50%→100%灰度，发现问题及时回滚
**效果**: 发布风险降低90%，回滚影响范围小
**验证**: 30+次 | 2026-04-14

### Pattern 2: 集中兵力发布
**发现场景**: 同时发布多个功能，互相影响，排查问题困难
**做法**: 每次发布聚焦核心目标，功能解耦
**效果**: 发布可控，问题可定位
**验证**: 20+次 | 2026-04-12

### Pattern 3: 部署即代码
**发现场景**: 手动部署，环境不一致，问题难复现
**做法**: Infrastructure as Code，环境可复现，可版本控制
**效果**: 部署一致性100%，问题复现时间从小时→分钟
**验证**: 18+次 | 2026-04-10

### Pattern 4: 持久化闭环
**发现场景**: 发布完成后经验没记录，下次又踩坑
**做法**: 发布后强制复盘，归档到learned-patterns
**效果**: 重复问题减少80%
**验证**: 15+次 | 2026-04-08

## ❌ Anti-Patterns (反模式)

### Anti-Pattern 1: 深夜发布
**问题场景**: 凌晨发布出问题，响应不及时
**问题表现**: 问题发现晚，处理慢，回滚决策难
**根本原因**: 发布选在人员最少的时候
**解决方案**:
1. 核心功能在工作时间发布
2. 非紧急更新在低峰期发布
3. 值班机制确保发布后有支持
**教训**: 发布的目的是成功，不是证明你可以凌晨工作。

### Anti-Pattern 2: 回滚方案缺失
**问题场景**: 发布出问题，但没有快速回滚方案
**问题表现**: 回滚花了2小时，影响扩大
**根本原因**: 只计划了"怎么发布"，没计划"怎么回滚"
**解决方案**:
1. 每个发布必须有回滚方案和执行时间估计
2. 回滚方案需要测试
3. 关键数据备份在发布前完成
**教训**: 没有回滚方案的发布是赌博。

### Anti-Pattern 3: 监控发布后观望
**问题场景**: 发布后看几眼日志，没问题就下班
**问题表现**: 渐进问题没被发现，过了黄金时间才发现
**根本原因**: 缺乏系统性监控
**解决方案**:
1. 发布后至少30分钟密集监控
2. 设置关键指标告警阈值
3. canary watch监控新版本与基线的差异
**教训**: 发布不是结束，是监控的开始。

### Anti-Pattern 4: 一次性全量发布
**问题场景**: 直接全量发布，出了问题全部用户受影响
**问题表现**: 问题发现时已经无法控制影响范围
**根本原因**: 急于求成，省略灰度步骤
**解决方案**:
1. 强制灰度发布流程
2. 每阶段设置通过标准
3. 自动化canary分析
**教训**: 再快的全量发布也比不过慢速灰度。
