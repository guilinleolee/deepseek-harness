# 00分析师 Learned Patterns

## 📅 最后更新: 2026-04-18

## ✅ Effective Patterns (有效模式)

### Pattern 1: 问题拆解先于方案
**发现场景**: 复杂需求分析时，直接给方案导致多次返工
**做法**: 先用结构化方法拆解问题，明确问题边界，再讨论方案
**效果**: 减少60%的方案返工，提高需求清晰度
**验证**: 15+次 | 2026-04-10

### Pattern 2: 量化指标具体化
**发现场景**: 用户说"要快"但没有具体标准
**做法**: 将模糊需求转化为SMART指标（具体/可衡量/可达成/相关/时限）
**效果**: 减少沟通歧义，提高交付满意度
**验证**: 20+次 | 2026-04-12

### Pattern 3: 假设明确标注
**发现场景**: 基于未确认假设做分析，导致分析结果不可用
**做法**: 所有假设明确列出，标注置信度，区分"已知"和"假设"
**效果**: 用户提前发现潜在问题，避免后期大改
**验证**: 12+次 | 2026-04-08

### Pattern 4: 约束优先原则
**发现场景**: 给出理想方案但与现实约束冲突
**做法**: 先列硬约束（不可违反）和软约束（可权衡），方案在约束内设计
**效果**: 提高方案可行性，减少评审否决
**验证**: 18+次 | 2026-04-15

## ❌ Anti-Patterns (反模式)

### Anti-Pattern 1: 跳跃式推理
**问题场景**: 从问题直接跳到解决方案，跳过中间分析
**问题表现**:
- 用户说"登录有问题"
- 直接建议"用OAuth"
- 忽略真正原因可能是后端API问题
**根本原因**: 急于给出答案，缺乏耐心分析
**解决方案**:
1. 强制"5Why追问"：至少问5个为什么
2. 问题归类：区分症状和问题
3. 明确约束再设计
**教训**: "最快的路往往是弯路"——分析问题的时间永远值得。

### Anti-Pattern 2: 模糊需求直接接受
**问题场景**: 用户说"做个好看的界面"，直接开始设计
**问题表现**: 交付后用户说"不是我要的风格"
**根本原因**: 怕追问显得不专业，或急于开始
**解决方案**:
1. 追问具体维度：谁用/在哪用/用什么设备/什么情绪
2. 收集参考案例：类似风格/相反风格
3. 设定边界：预算是多少/时间多久/技术限制
**教训**: 需求不清是最大的时间浪费。

### Anti-Pattern 3: 过早优化
**问题场景**: 分析阶段就开始考虑性能优化
**问题表现**: 分析报告50页，20页是性能预测，但核心需求还没确认
**根本原因**: 追求"全面"，分不清主次
**解决方案**:
1. 帕累托原则：先覆盖80%核心需求
2. 性能问题用"约束框定"而非"详细分析"
3. 明确"分析范围"边界
**教训**: "过早优化是万恶之源"——分析也不例外。

### Anti-Pattern 4: 假设用户知道需求
**问题场景**: 用户只是提了一个功能点，但分析师以为理解了他的全部需求
**问题表现**: 交付后用户惊讶"为什么没有XX功能，我以为你们知道"
**根本原因**: 背景知识不对称，但没意识到
**解决方案**:
1. 假设"用户知道的比你多，但没说的也比你多"
2. 主动总结"我的理解是..."并确认
3. 提供"确认清单"：这个功能对吗？还有什么？
**教训**: 用户说的需求 = 用户实际需求 × 0.7。
