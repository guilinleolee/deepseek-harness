## ✅ Effective Patterns (有效模式)

### Pattern 1: 极端验证找茬
**发现场景**: 测试覆盖了正常路径，边界情况上线后全炸
**做法**: 刻意找茬：空值/最大最小/并发/异常网络，验证每个边界
**效果**: 边界bug减少80%
**验证**: 30+次 | 2026-04-12

### Pattern 2: 证据验证六维框架
**发现场景**: 结论缺乏证据支撑，质量判断主观
**做法**: 从来源质量/事实准确性/逻辑严密性/覆盖全面性/实用价值/局限性说明六维验证
**效果**: 验证准确率提升60%
**验证**: 20+次 | 2026-04-14

### Pattern 3: 回归测试自动化
**发现场景**: 每次修改担心影响现有功能，靠手工回归
**做法**: 建立自动化回归测试套件，CI/CD集成，修改即触发
**效果**: 回归时间从2小时→5分钟
**验证**: 15+次 | 2026-04-10

### Pattern 4: 失败模式分析
**发现场景**: 只测功能是否工作，不测如何失败
**做法**: FMEA思维：列出可能的失效模式，验证系统在各种失败场景下的行为
**效果**: 系统可靠性提升，MTBF延长
**验证**: 12+次 | 2026-04-08

## ❌ Anti-Patterns (反模式)

### Anti-Pattern 1: 测试覆盖自欺欺人
**问题场景**: 代码覆盖率80%，但线上bug不断
**问题表现**:
- 只测Happy Path
- Mock数据与生产差异大
- 断言永远为true
**根本原因**: 覆盖率是数字，不是质量
**解决方案**:
1. 关注分支覆盖，不是行覆盖
2. 使用生产数据采样测试
3. 断言必须验证具体值，不是存在性
**教训**: 测了不等于测对了。

### Anti-Pattern 2: 跳过不稳定测试
**问题场景**: 间歇性失败的测试被跳过，久而久之忘了修
**问题表现**: 测试套件有20个skip标记
**根本原因**: 不稳定测试=信号弱，不处理=信号消失
**解决方案**:
1. 调查不稳定原因：时序/并发/网络/资源竞争
2. 隔离不稳定测试，优先修复
3. 设置flaky test监控，超过阈值自动告警
**教训**: 跳过的测试是欠下的债。

### Anti-Pattern 3: 事后验证而非测试驱动
**问题场景**: 代码写完后补测试，测试只是为了覆盖率指标
**问题表现**: 测试与实现耦合，修改代码需要同时修改测试
**根本原因**: 测试是 afterthought，不是设计的一部分
**解决方案**:
1. TDD：测试先于实现
2. 测试是代码的客户端视角
3. 测试驱动接口设计
**教训**: 测试驱动设计，设计驱动实现。

### Anti-Pattern 4: 验证结论不记录
**问题场景**: 验证了某个方案可行，但没记录依据
**问题表现**: 三个月后有人质疑，又要从头验证一遍
**根本原因**: 验证结果没有归档
**解决方案**:
1. 每个验证结论记录：验证方法/数据/结论/置信度
2. 归档到learned-patterns或Wiki
3. 关键验证需要交叉验证
**教训**: 验证一次，多人受益。
