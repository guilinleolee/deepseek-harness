# dbs-deconstruct

## L0: 一句话描述
需求解构——基于维特根斯坦语言哲学，将模糊需求拆解为可执行的原子级子任务。

## L1: 使用场景
当用户提出模糊、多层次或复杂的任务时使用。通过"边界定义→层次分解→原子化→依赖建模→优先级排序"五步，将需求转化为可量化、可执行、可追踪的子任务树。解决需求模糊、范围蔓延、执行混乱问题。

## L2: 详细文档

### 核心能力
基于维特根斯坦语言哲学（"语言的边界就是世界的边界"），通过语义解析→边界划定→层次分解→原子化→依赖建模五步，将模糊需求转化为原子级任务树。

### 需求模糊度评估

```markdown
┌─────────────────────────────────────────────────────────────┐
│ 需求模糊度光谱                                           │
├─────────────────────────────────────────────────────────────┤
│ L1: 完全明确（无歧义）                                   │
│     - 有具体交付物                                       │
│     - 有明确完成标准                                     │
│     - 无需追问，可直接执行                               │
│                                                             │
│ L2: 部分模糊（可澄清）                                   │
│     - 有主要目标，细节待定                               │
│     - 需要1-2轮追问澄清                                 │
│     - 可分解但需边界确认                                │
│                                                             │
│ L3: 中度模糊（需解构）                                  │
│     - 多层次、多角色交织                                │
│     - 需要结构化分解                                     │
│     - 依赖关系复杂                                       │
│                                                             │
│ L4: 高度模糊（需探索）                                  │
│     - 目标本身不清晰                                    │
│     - 需要先澄清再分解                                  │
│     - 建议先调用 dbs-diagnosis                         │
│                                                             │
│ L5: 完全模糊（需洞察）                                   │
│     - 用户自己也说不清                                 │
│     - 需要深层需求挖掘                                   │
│     - 建议先调用 dbs-austrian                         │
└─────────────────────────────────────────────────────────────┘
```

### 五步解构流程

```markdown
Step 1: 边界定义
  - 识别需求的语义边界（做什么/不做什么）
  - 标注关键术语和隐含假设
  - 区分"必要条件"和"充分条件"

Step 2: 层次分解
  - 按执行逻辑划分任务层次（战略→战术→执行）
  - 识别每层的输入、输出、约束
  - 建立层次间的信息传递关系

Step 3: 原子化
  - 将每个任务分解为原子操作（不可再分）
  - 原子任务定义：单一角色可完成、有明确输出、可独立验证
  - 标注复合任务需进一步拆分

Step 4: 依赖建模
  - 识别任务间的依赖关系（顺序/并行/条件）
  - 构建任务依赖图（DAG）
  - 识别关键路径和并行机会

Step 5: 优先级排序
  - 基于依赖关系确定执行顺序
  - 标注紧急度和重要性
  - 识别可并行执行的任务组
```

### 任务原子化标准

| 标准 | 说明 | 自检问题 |
|------|------|---------|
| **角色单一** | 一个执行者/角色可完成 | "谁来执行？" |
| **输出明确** | 有具体的交付物 | "完成后交付什么？" |
| **可独立验证** | 有明确的完成标准 | "如何判断完成？" |
| **无内部依赖** | 不依赖其他子任务 | "还需要等什么？" |
| **时间可估** | 预计工时在合理范围 | "预计多长时间？" |

### 依赖关系类型

| 类型 | 符号 | 说明 | 示例 |
|------|------|------|------|
| **FS** | → | 完成开始（Finish-Start） | 任务A完成后开始B |
| **FF** | ↔ | 完成完成（Finish-Finish） | A和B同时完成 |
| **SS** | ≈ | 开始开始（Start-Start） | A和B同时开始 |
| **SF** | ⇒ | 开始完成（Start-Finish） | B在A开始后结束 |
| **条件** | ◇ | 条件依赖 | B依赖A的输出结果 |

### 使用命令

```bash
/dbs-deconstruct              # 启动解构分析
/dbs-deconstruct "需求描述"  # 直接分析
/dbs-deconstruct --deep       # 深度解构（含依赖建模）
/dbs-deconstruct --quick      # 快速解构（仅分解）
/dbs-deconstruct --output md  # 输出为Markdown格式
```

- [ ] 任务依赖关系已完整建模
- [ ] 关键路径和并行机会已识别
- [ ] 优先级排序有明确理由
- [ ] 分解结果已与用户确认

### 禁忌

- ❌ 不评估模糊度直接解构（从L5开始解构L1需求）
- ❌ 将复合任务当作原子任务（"写代码"不是原子）
- ❌ 忽视隐含假设（未标注"假设X成立"）
- ❌ 不建模依赖关系（导致执行顺序混乱）
- ❌ 跳过优先级排序（眉毛胡子一把抓）
- ❌ 分解过细（L1需求无需分解到P3任务）
- ❌ 分解不足（L4需求只分到L1就停止）
