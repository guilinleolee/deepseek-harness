# mvp-scope-limiter (MVP范围守护者)

## L0: 一句话描述 (≤15字)
守护MVP边界，防止范围蔓延

## L1: 使用场景 (50-100字)
在MVP开发过程中，实时保护MVP边界。当有人（或者你自己）想要往MVP里加功能时，用这个技能判断：这个功能应该加吗？还是应该放到v2？

## L2: 详细文档

### 核心原则

**MVP不是"缩小版产品"，而是"最小可验证实验"。**

MVP的唯一目的是回答一个问题：**有人愿意付钱吗？**

如果一个功能不能帮你回答这个问题，它就不是MVP的一部分。

### 添加功能的黄金法则

**对于任何想要添加的功能，问以下3个问题**：

```
问题1: 去掉了会死吗？
   如果没有这个功能，产品还能验证核心价值主张吗？
   → 能: 暂时不加
   → 不能: 继续问问题2

问题2: 能在1周内完成吗？
   如果超过1周，这个功能应该在v2
   → 能: 继续问问题3
   → 不能: 放入v2 backlog

问题3: 现在做还是以后做？
   即使功能很棒，如果阻碍了核心价值验证，它就应该等
   → 现在: 立即实现
   → 以后: 放入v2 backlog
```

### MVP vs v2清单

**MVP中必须有 (不可删除)**：
- [ ] 核心价值交付：用户使用产品后能得到什么？
- [ ] 支付系统：没有收入就没有生意
- [ ] 用户账户：至少能注册、登录
- [ ] 数据持久化：用户数据不会丢失

**MVP中不应该有 (v2再做)**：
- ❌ 用户反馈系统 → 手动收集邮件
- ❌ 多用户/权限系统 → 先单用户
- ❌ 高级分析仪表板 → 先用Excel
- ❌ 邀请/协作功能 → 先单人使用
- ❌ 移动端App → 先Web响应式
- ❌ 国际化 → 先单一语言
- ❌ 自动化邮件 → 手动发送
- ❌ API接口 → 直接在产品里用

**MVP灰色地带 (根据情况判断)**：
- ⚠️ 邮箱验证 → 如果spam是个问题就做
- ⚠️ 密码重置 → 如果用户频繁需要就做
- ⚠️ 数据导出 → 如果用户数据重要就做
- ⚠️ 帮助文档 → 如果产品自解释就不做

### 开发时间保护

**1周法则**：
- 如果一个功能预计需要超过1周，它就不是MVP
- 拆分功能，直到每个功能<1周
- 如果不能拆分，延长到2周，但不能更长了

**每日站会问题**：
```
今天结束时：
1. 今天的代码让核心价值验证更近了吗？
2. 有什么意外的范围蔓延正在发生？
3. 明天要做什么来保护MVP边界？
```

### 常见范围蔓延模式

| 蔓延模式 | 信号 | 应对 |
|---------|------|------|
| **"这只是个小功能"** | 频繁添加小功能 | 累计超过3个就该暂停 |
| **"竞品有这个"** | 看到竞品有就想加 | 先问：它验证了核心价值吗？ |
| **"等XX一起做"** | 推迟核心功能 | 先独立验证，再整合 |
| **"等它完美再做"** | 追求完美而非验证 | MVP是实验，不是产品 |
| **"用户会需要这个"** | 假设用户需求 | 用户说过他们需要吗？ |

### 使用命令

```bash

/mvp-scope-limit

# 或自然语言触发
[@99-01] 评估这个功能是否应该加入MVP: [功能描述]

# 每日保护检查
[@99-01] 今天有范围蔓延吗？
```

### 关键心态

> **记住**：你的目标不是做一个完整的产品，而是用最少的功能验证一个假设。如果假设被验证了，你有整个未来来完善它。如果假设被证伪了，你庆幸没有花6个月做一个没人要的产品。
