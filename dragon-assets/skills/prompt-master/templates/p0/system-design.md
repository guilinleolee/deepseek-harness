# Examples (示例)

### 示例1: 电商秒杀系统

**需求**: 支持百万用户在1分钟内抢购1万件商品

**核心设计**:
```
架构模式: 异步削峰+缓存兜底
核心组件:
1. CDN + 静态化: 商品详情页静态化，抗压>100万QPS
2. Redis集群: 库存预热，原子扣减，支持高并发
3. 消息队列: 异步下单，削峰填谷
4. 限流策略: 令牌桶+用户级限流，防刷
5. 降级预案: 库存不足时直接返回友好提示

技术栈:
- 缓存: Redis Cluster
- 消息队列: Kafka
- 限流: Sentinel
- 数据库: MySQL分库分表
```

### 示例2: 实时通信系统

**需求**: 支持10万用户同时在线聊天，消息延迟<100ms

**核心设计**:
```
架构模式: 长连接+消息路由
核心组件:
1. 网关层: WebSocket长连接，负载均衡
2. 路由层: 基于用户ID的一致性哈希路由
3. 消息存储: Cassandra写扩散+读扩散混合
4. 推送服务: 客户端心跳保活，断线重连

技术栈:
- 协议: WebSocket
- 网关: Netty
- 存储: Cassandra + Redis
```

# Additional (附加信息)

## 设计原则

### 1. 简单性优先
- 避免过度设计
- 优先选择成熟技术
- 减少组件数量

### 2. 可演进性
- 预留扩展点
- 模块化设计
- 接口隔离

### 3. 可观测性
- 全链路追踪
- 指标监控
- 日志聚合

### 4. 高可用性
- 服务降级
- 熔断限流
- 异地多活

## 常见架构模式

| 模式 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| 分层架构 | 传统Web应用 | 职责清晰，易于理解 | 层间耦合，性能损耗 |
| 微服务 | 复杂业务，快速迭代 | 独立部署，技术异构 | 分布式复杂，运维成本高 |
| 事件驱动 | 高并发，松耦合 | 异步解耦，削峰填谷 | 一致性难保证，调试复杂 |
| CQRS | 读写分离场景 | 性能优化，读写独立 | 复杂度高，最终一致性 |

## 常见误区

1. **过度设计**: 一上来就上微服务/Kafka，实际业务简单
2. **忽视性能**: 设计阶段不考虑索引、缓存，上线后性能问题
3. **忽视安全**: 没有认证授权、数据加密
4. **忽视运维**: 没有监控、日志，出问题无法排查
5. **忽视成本**: 选择昂贵方案，实际用不到
6. **忽视团队能力**: 选择团队不熟悉的技术，学习成本高

## 输出建议

- **图表优先**: 使用Mermaid图示，一图胜千言
- **量化决策**: 用数据支撑技术选型（如"Redis支持10万QPS"而非"Redis很快"）
- **场景驱动**: 设计必须基于具体场景，避免泛泛而谈
- **迭代演进**: 给出分阶段实施计划，而非一步到位

## 注意事项

1. **理解业务**: 技术服务于业务，不要为了技术而技术
2. **简单优先**: 复杂的系统往往是失败的系统
3. **度量驱动**: 架构决策要有明确的度量指标
4. **演进思维**: 架构是演进的，不是一步到位的
5. **成本意识**: 考虑TCO（总拥有成本），不仅是开发成本
