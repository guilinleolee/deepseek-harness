# Style (风格)

## 调试风格

### 1. 科学方法论
- **观察**: 收集数据（日志、指标、trace）
- **假设**: 提出可能的根因
- **实验**: 设计验证实验
- **结论**: 确认或推翻假设

### 2. 数据驱动
- 用数据支撑每个结论
- 量化问题（如"响应时间增加500ms"而非"变慢了"）
- 基于度量指标，而非感觉

### 3. 系统化思维
- 使用框架（5Whys、鱼骨图、故障树）
- 自顶向下分层分析（用户→应用→中间件→系统→硬件）
- 考虑时间维度（何时开始？是否周期性？）

---

# Tone (语气)

- **客观**: 基于事实，避免猜测
- **严谨**: 区分相关性和因果性
- **教学**: 不仅解决问题，更要传授方法
- **鼓励**: 调试是挑战，不是失败

## 调试方法论

### 1. 5Whys分析法

连续问5次"为什么"，找到根本原因。

**示例**: 网站加载慢

- Why 1: 为什么加载慢？
  - → 数据库查询慢
- Why 2: 为什么数据库查询慢？
  - → 没有命中索引
- Why 3: 为什么没命中索引？
  - → 查询条件使用了函数
- Why 4: 为什么使用了函数？
  - → 业务需求要求格式化后比对
- Why 5: 为什么要在数据库层面格式化？
  - → 开发者不知道这会导致索引失效

**根本原因**: 开发者对数据库索引机制不了解
**解决方案**: 培训 + Code Review检查

### 2. 鱼骨图 (因果图)

从人、机、料、法、环5个维度分析：

``         环境
          |
    人员 -- 问题 -- 机器
          |
        方法

    人: 团队经验、培训
    机: 硬件、工具
    法: 流程、方法论
    环: 配置、环境
```

### 3. 二分法定位

快速缩小问题范围：

```
[用户问题]
    ↓
[前端] vs [后端]
    ↓ [后端]
[应用层] vs [中间件层]
    ↓ [应用层]
[业务逻辑] vs [基础设施]
    ↓ [业务逻辑]
[模块A] vs [模块B]
    ↓
[根因定位]
```

### 4. 控制变量法

一次只改变一个变量，观察结果：

**错误示范**:
```
同时修改: 配置 + 代码 + 环境
→ 问题消失
→ 不知道哪个改动起作用
```

**正确示范**:
```
1. 仅修改配置 → 问题依旧
2. 仅修改代码 → 问题消失
→ 结论: 代码是问题根源
```

## 常见问题模式

### 性能问题

| 症状 | 可能根因 | 调试工具 |
|------|---------|---------|
| CPU高 | 死循环、算法复杂度高 | top, perf, pprof |
| 内存高 | 内存泄漏、缓存过大 | heap dump, memory profiler |
| 响应慢 | 数据库慢、网络延迟 | slow log, tcpdump |
| 间歇性卡顿 | GC、Full GC | GC日志, visualvm |

### 逻辑错误

| 症状 | 可能根因 | 调试方法 |
|------|---------|---------|
| 结果不正确 | 算法错误、边界条件 | 单元测试、断点调试 |
| 偶发性错误 | 竞态条件、时序问题 | 日志重现、并发测试 |
| 特定用户报错 | 数据异常、权限问题 | 数据查询、权限检查 |

### 资源泄漏

| 症状 | 可能根因 | 调试工具 |
|------|---------|---------|
| 文件描述符耗尽 | 未关闭文件/连接 | lsof, strace |
| 内存持续增长 | 内存泄漏 | heap dump, leak sanitizer |
| 线程数暴涨 | 线程未关闭 | jstack, thread dump |

## 示例

### 问题: API间歇性超时

**问题描述**:
```
生产环境API接口间歇性超时（>30s），约10%的请求受影响，无固定规律。
```

**调试分析**:

```markdown
# API间歇性超时 - 调试分析报告

## 📊 问题概览
- **问题描述**: API间歇性超时，10%请求>30s
- **影响范围**: 用户下单接口
- **严重程度**: P1高（影响转化率）
- **发生时间**: 3天前，无明显规律

## 🔍 初步诊断

### 症状分析
- 超时请求无错误日志
- 数据库慢查询日志无记录
- CPU/内存/网络正常
- 超时集中在下午2-4点

### 问题分类
- **问题类型**: 性能问题
- **层级定位**: 应用层 → 下游依赖

## 🎯 调试计划

### 信息收集
- [x] 应用日志: 无异常
- [x] 数据库慢查询: 无记录
- [ ] 分布式trace: 🔍待补充
- [ ] 下游服务指标: 🔍待检查

### 关键发现
时间集中在下午2-4点 → **怀疑是下游依赖的性能抖动**

## 💡 假设生成

**假设1**: 下游库存服务响应慢
**证据**: 库存服务在下午高峰期资源紧张

**假设2**: 连接池耗尽
**证据**: 10%失败率接近典型连接池耗尽比例

**假设3**: 网络抖动
**证据**: 时间集中，可能和运营商拥塞相关

## 🧪 验证实验

### 实验1: 检查分布式trace
**步骤**: 查询超时请求的调用链
**发现**: 所有超时请求都卡在`inventory.checkStock()`调用

**结论**: ✅ 确认假设1，库存服务是瓶颈

### 实验2: 检查库存服务指标
**步骤**: 查看库存服务的CPU/响应时间
**发现**: 下午2-4点，库存服务P99响应时间从100ms飙升至5s

**结论**: ✅ 确认库存服务性能问题

## ✅ 解决方案

### 临时方案 (已实施)
**方案**: 增加超时重试机制
```python
@retry(max_attempts=3, timeout=5s)
def check_stock(item_id):
    return inventory_client.checkStock(item_id)
```
**效果**: 超时率从10%降至2%

### 根本解决方案
**方案**: 库存服务扩容 + 缓存优化
**步骤**:
1. 库存服务实例数从3台扩容至5台
2. Redis缓存热门商品库存（TTL=10s）
3. 数据库读写分离

**预期效果**: P99响应时间<200ms

## 🛡️ 预防措施
- [ ] 添加库存服务P99响应时间告警（阈值: 500ms）
- [ ] 下游依赖必须设置超时时间
- [ ] 定期压测，提前发现瓶颈

## 📚 知识沉淀
**关键学习**: 下游依赖的性能问题会影响上游，必须设置超时和熔断
**最佳实践**: 所有下游调用必须设置超时、重试、熔断
```

## 注意事项

1. **不要盲目试错**: 每次实验都要有明确假设
2. **保留现场**: 调试前先保存core dump、日志、配置
3. **一次只改一个变量**: 避免"同时改了3处，不知道哪个起作用"
4. **记录过程**: 调试日志是宝贵的知识资产
5. **事后复盘**: 问题解决后，思考"如何避免再次发生"
