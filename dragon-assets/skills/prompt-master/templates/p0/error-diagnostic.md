# Style (风格)

## 诊断风格

### 1. 系统化方法
- **信息收集**: 收集日志、指标、配置、变更记录
- **假设生成**: 基于证据提出可能的根因
- **验证实验**: 设计实验验证假设
- **根因确认**: 确认根本原因，而非表面症状

### 2. 分析工具
- **5Whys分析法**: 连续问5次"为什么"
- **鱼骨图**: 从人、机、料、法、环5个维度分析
- **二分法**: 快速缩小问题范围
- **时间线分析**: 回溯问题发生时间点前后的变化

### 3. 诊断流程
```
1. 理解问题 → 2. 收集信息 → 3. 生成假设
→ 4. 验证假设 → 5. 定位根因 → 6. 提出方案
```

### 示例1: 数据库连接错误诊断

**错误信息**:
```
Error: connect ETIMEDOUT
  at Connection._handleConnectTimeout
  at TCPConnectWrap.afterConnect [as oncomplete]
```

**上下文**:
```
Node.js应用，连接PostgreSQL数据库
最近数据库迁移到新服务器
间歇性超时，约10%的请求失败
```

**诊断报告**:

```markdown
# 数据库连接超时 - 诊断报告

## 📊 错误概览

### 错误信息
```
Error: connect ETIMEDOUT
  at Connection._handleConnectTimeout
```

### 发生时间
- 首次发现: 3天前（数据库迁移后）
- 发生频率: 间歇性，约10%请求失败

### 影响范围
- **影响用户**: 全部用户
- **影响功能**: 所有需要数据库的功能
- **严重程度**: P1高（影响核心功能）

---

## 🔍 初步分析

### 症状描述
- 数据库连接间歇性超时
- 错误率约10%
- 超时集中在业务高峰期（下午2-4点）
- 数据库慢查询日志无记录

### 错误分类
- **错误类型**: 网络问题 + 资源耗尽
- **层级定位**: 网络层 → 应用层
- **影响范围**: 全部应用实例

---

## 💡 根因分析（5Whys）

### Why 1: 为什么连接超时？
→ TCP三次握手超时，数据库服务器未响应

### Why 2: 为什么数据库服务器未响应？
→ 数据库服务器CPU 100%，无法处理新连接

### Why 3: 为什么CPU 100%？
→ 有慢查询占用大量CPU资源

### Why 4: 为什么有慢查询？
→ 新迁移的数据库缺少索引

### Why 5: 为什么缺少索引？
→ 迁移脚本未包含索引创建，且迁移后未验证

### 根因结论
**根本原因**: 数据库迁移时未创建索引，导致慢查询消耗CPU，连接池耗尽

---

## 🧪 验证实验

### 实验1: 检查数据库CPU
**命令**: `top -p $(pgrep postgres)`
**发现**: 数据库进程CPU 100%
**结论**: ✅ 确认数据库资源耗尽

### 实验2: 检查慢查询
**命令**: 查看慢查询日志
**发现**: 5个查询每次执行>10秒，全表扫描
**结论**: ✅ 确认存在慢查询

### 实验3: 检查索引
**命令**: `\d table_name`
**发现**: 关键字段缺少索引
**结论**: ✅ 确认缺少索引是根本原因

---

## ✅ 解决方案

### 临时方案（已实施）
**方案**: 增加数据库连接池超时时间
**代码**:
```javascript
const pool = new Pool({
  host: 'db.example.com',
  max: 20,
  connectionTimeoutMillis: 10000,  // 从2000ms增加到10000ms
  idleTimeoutMillis: 30000
});
```
**效果**: 超时率从10%降至3%

### 根本解决方案
**方案**: 创建缺失的索引
**步骤**:
1. 分析慢查询，识别需要索引的字段
2. 创建索引:
```sql
CREATE INDEX idx_user_email ON users(email);
CREATE INDEX idx_order_created ON orders(created_at);
```
3. 验证查询性能:
```sql
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'test@example.com';
```
4. 监控数据库CPU和慢查询

**预期效果**: CPU从100%降至30%，慢查询消失

### 示例2: 内存泄漏诊断

**错误信息**:
```
JavaScript heap out of memory
FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript heap out of memory
```

**上下文**:
```
Node.js服务，运行24小时后内存持续增长
最终触发OOM，进程崩溃
重启后恢复正常，但循环往复
```

**诊断报告**:

```markdown
# Node.js内存泄漏 - 诊断报告

## 📊 错误概览

### 错误信息
```
JavaScript heap out of memory
```

### 发生时间
- 首次发现: 1周前
- 发生频率: 持续，每24小时崩溃一次

### 影响范围
- **影响用户**: 全部用户
- **影响功能**: 服务不可用（进程崩溃）
- **严重程度**: P0紧急

---

## 💡 根因分析（5Whys）

### Why 1: 为什么内存溢出？
→ Node.js堆内存超过上限（1.4GB）

### Why 2: 为什么堆内存持续增长？
→ 有对象无法被垃圾回收（内存泄漏）

### Why 3: 为什么对象无法被回收？
→ 全局变量持有了大量对象的引用

### Why 4: 为什么全局变量持有引用？
→ 代码中有缓存逻辑，将请求数据存入全局对象，未设置过期时间

### Why 5: 为什么未设置过期时间？
→ 开发者忽略了缓存清理机制

### 根因结论
**根本原因**: 全局缓存对象无限增长，未设置过期时间和上限

---

## 🧪 验证实验

### 实验1: Heap Snapshot分析
**工具**: Chrome DevTools Memory
**步骤**:
1. 启动应用，记录初始Heap Snapshot
2. 运行24小时，记录第二个Heap Snapshot
3. 对比两个Snapshot

**发现**: `globalCache`对象从10MB增长到1.2GB

**结论**: ✅ 确认globalCache是内存泄漏源

### 实验2: 代码审查
**问题代码**:
```javascript
// ❌ 差: 全局缓存，无清理机制
const globalCache = {};

app.get('/api/users', (req, res) => {
  const cacheKey = req.query.id;
  globalCache[cacheKey] = fetchUser(req.query.id);  // 持续累积
  res.json(globalCache[cacheKey]);
});
```

**结论**: ✅ 确认缓存逻辑有问题

---

## ✅ 解决方案

### 临时方案（已实施）
**方案**: 增加Node.js堆内存上限
**命令**:
```bash
node --max-old-space-size=4096 app.js  # 从1.4GB增加到4GB
```
**效果**: 崩溃周期从24小时延长至72小时

### 根本解决方案
**方案**: 使用LRU Cache，限制缓存大小

**修复代码**:
```javascript
// ✅ 好: 使用LRU Cache，自动清理
const LRU = require('lru-cache');
const globalCache = new LRU({
  max: 500,                    // 最多缓存500条
  ttl: 1000 * 60 * 10,         // 10分钟过期
  updateAgeOnGet: true         // 访问时更新过期时间
});

app.get('/api/users', (req, res) => {
  const cacheKey = req.query.id;

  // 检查缓存
  if (globalCache.has(cacheKey)) {
    return res.json(globalCache.get(cacheKey));
  }

  // 查询数据
  const user = await fetchUser(req.query.id);

  // 写入缓存（自动淘汰旧数据）
  globalCache.set(cacheKey, user);

  res.json(user);
});
```

**效果**: 内存稳定在200MB，不再增长

### 示例3: API超时错误诊断

**错误信息**:
```
Error: Request timeout after 30000ms
  at Timeout.setTimeout [as _onTimeout]
```

**上下文**:
```
微服务架构，服务A调用服务B
最近发布新版本后，间歇性超时
约5%的请求超时30秒
```

**诊断报告**:

```markdown
# API超时错误 - 诊断报告

## 📊 错误概览

### 错误信息
```
Error: Request timeout after 30000ms
```

### 发生时间
- 首次发现: 2天前（新版本发布后）
- 发生频率: 间歇性，约5%请求超时

### 影响范围
- **影响用户**: 5%用户
- **影响功能**: 调用服务B的功能
- **严重程度**: P1高

---

## 💡 根因分析（5Whys）

### Why 1: 为什么API超时？
→ 服务A在30秒内未收到服务B的响应

### Why 2: 为什么服务B未响应？
→ 服务B的处理时间偶尔超过30秒

### Why 3: 为什么处理时间变长？
→ 服务B在处理某些请求时需要调用第三方API

### Why 4: 为什么第三方API响应慢？
→ 第三方API有速率限制，超过后请求被排队

### Why 5: 为什么没有错误处理？
→ 新版本代码未添加超时重试和降级逻辑

### 根因结论
**根本原因**: 第三方API速率限制导致请求排队，缺少超时重试和降级机制

---

## 🧪 验证实验

### 实验1: 检查服务B日志
**发现**: 超时请求都在调用第三方API，等待时间>30秒
**结论**: ✅ 确认第三方API是瓶颈

### 实验2: 检查第三方API文档
**发现**: 速率限制为10请求/秒，超过返回429
**结论**: ✅ 确认触发速率限制

### 实验3: 压力测试
**场景**: 模拟高并发调用
**发现**: 超过10 QPS后，响应时间急剧增加
**结论**: ✅ 确认速率限制是根本原因

---

## ✅ 解决方案

### 临时方案（已实施）
**方案**: 增加服务A的超时时间
**代码**:
```javascript
await axios.get('http://service-b/api', {
  timeout: 60000  // 从30秒增加到60秒
});
```
**效果**: 超时率从5%降至2%

### 根本解决方案
**方案**: 添加超时重试 + 降级逻辑

**修复代码**:
```javascript
const axios = require('axios');
const retry = require('retry');

// 配置重试策略
const retryOptions = {
  retries: 3,
  factor: 2,        // 指数退避
  minTimeout: 1000, // 1秒
  maxTimeout: 10000 // 10秒
};

async function callServiceB() {
  try {
    await retry(async (bail) => {
      try {
        const response = await axios.get('http://service-b/api', {
          timeout: 5000,  // 5秒超时
          headers: {
            'Retry-Count': retry.attempt()
          }
        });
        return response.data;
      } catch (error) {
        if (error.response?.status === 429) {
          // 429 Too Many Requests，重试
          throw error;  // 触发重试
        } else {
          // 其他错误，不重试
          bail(error);
        }
      }
    }, retryOptions);
  } catch (error) {
    // 重试失败，降级处理
    return getFallbackData();
  }
}
```

**降级逻辑**:
```javascript
function getFallbackData() {
  // 返回缓存数据或默认值
  return {
    status: 'degraded',
    data: getCachedData() || getDefaultData()
  };
}
```

**效果**:
- 超时率从5%降至0.1%
- 即使第三方API故障，也能返回降级数据
