# Agent Note: 内容日历升级为排期工作台——事件即存储的排期条目本身

Status: proposed

[English](2026-09-27-content-calendar-scheduling-workbench.md) | 中文

## Problem

内容创作插件的内容日历原本只是覆盖 `_schedule.json` 的裸月视图，而日历栏目的开发提示词（v1）要求的是完整排期工作台——月/周/列表三视图、拖拽改期、筛选、冲突提醒、CSV 导出，以及与选题库和发布视图的双向联动。v1 的数据模型按原文无法实现：它既把日历事件说成源数据的派生视图，又说成带自有元数据的落库实体；宣称同步"单向"却同时反向回写；"删除日历事件"在下一次同步中原样复活；渲染时才可判定的逾期状态与存储态混在同一个枚举里。实现者只能自行发明缺失的模型，而每种发明都会以不同方式漂移。

并行开发的约束抬高了赌注：选题库已经在写排期条目并用 `scheduleItemId` 关联，发布视图（并行进行中）给 `_schedule.json` 记录扩展了可选字段 `publishTaskId`，而作品元数据文件 `.dsh-output.json` 是所有栏目的零接触文件。日历必须选一个不给这块磁盘面板增加第二事实源的数据模型。

## Proposal

**日历事件就是存储的 `ScheduleItem`，别无其他。** 排期条目是每个事件唯一的存储事实；日历唯一自有的数据是日期备注，存放在库根新增的 `_calendar.json` sidecar（`{ formatVersion: 0, notes: { [scheduleItemId]: { text, updatedAt } } }`），经两个新的 `contentSchedule` Remote 方法（`getNotes`/`putNote`）服务，沿用排期文件的同一套文件锁、原子写、未知版本拒载和 `problems` 告警。空文本写入即清除条目；指向已删条目的备注留存但失效。因为事件就是存储条目，"删除日历事件"就是删除它——v1 的复活问题从此不存在——而显式的"删除并清空选题计划时间"动作覆盖了唯一需要联动遗忘的场景。

**逾期与冲突是渲染时派生，绝不落盘。** `calendar.ts`（既有纯函数模块，依旧零 React 零 IO）新增周网格、逾期规则（计划日已过且从未发布）、冲突规则（同平台同日的两条 `scheduled` 时刻差小于 120 分钟——模块常量——或同平台同日三条及以上 `scheduled` 拥挤，全天条目只计入拥挤）、列表过滤、CSV 导出（UTF-8 with BOM、CRLF、固定中文列），以及整带回退的版本化 localStorage 视图配置迁移。localStorage 只承载视图/筛选配置（选题库已裁决的先例），业务数据零接触。

**改期先确认，再经网关写入。** 拖拽 chip 弹确认框，随后 `contentSchedule.put` 移动条目；当选题经 `scheduleItemId` 反向关联时，第二次 `contentTopics.put` 携带新计划日期，第二次写失败只 toast 不回滚第一次。FullCalendar 继续缺席：插件"不新增运行时依赖"的裁决维持，拖拽用与选题库看板相同的原生 HTML5 DnD，MIT 许可的 FullCalendar 保留为手写视图不再划算时的备选记录。AI 排期建议以禁用占位交付——插件零新增 AI 调用——发布联动仅限于读取可选字段 `publishTaskId`，待发布视图落地后点亮跳转。

## Alternatives considered

**v1 的混合模型：派生事件加 `<主题>/.dsh-output.json` 内的 overrides 记录。** 双重否决：`.dsh-output.json` 是带严格元数据门控的全栏目零接触文件；混合模型需要一套同步引擎加删除墓碑机制才能防止复活——而这些都在重新表示排期条目已经存好的事实。

**采用 FullCalendar 撑视图。** 月/周/列表与拖拽确是 MIT 且久经考验，但选题库手写看板拖拽时插件已裁决不新增运行时依赖；对同一个条目数组的三个视图还不足以推翻该裁决，其 CSS 也会与 `--dsw-alias-*` 令牌体系打架。

**给 `ScheduleItem` 扩一个 note 字段。** 少一个文件，但条目 schema 是跨栏目的冻结契约（选题库与发布都有代码压在上面），且备注是日历自有的注解而非排期事实——混入之后每个栏目的读取都要驮着日历的负载。

## 验收标准

- 左侧导航出现「内容日历」入口，视图以选题库与发布视图共用的同一份 `_schedule.json` 条目渲染月/周/列表三个标签。
- 月网格内跨单元格拖拽先弹确认，确认后移动条目——`content` 类条目同时经 topics 面回写关联选题的 `planDate`；取消则不动。
- 任何未发布且日期已过的条目渲染逾期标记：渲染期计算、绝不落库。
- 同平台 120 分钟内两条、或同日三条及以上已排期条目，触发冲突横幅与 chip 描边；调整窗口不需要动数据。
- 筛选栈（类型、平台 chip、状态 chip、日期范围、搜索、仅看逾期）可组合，按浏览器持久化并带版本键，未知版本整体回退。
- CSV 导出落入所选主题 `assets/`，UTF-8 带 BOM、CRLF 行尾，Excel 打开无乱码。
- 日备注活过工作台的一次关闭/重开：空写入即清除，未知 `_calendar.json` 版本拒载为命名问题，条目永不丢失排期真相。

## 风险

- 拖拽→选题 `planDate` 回写横跨两个面两个文件；排期写入先提交，选题写入失败会让条目已移动而选题计划日期滞后——下次打开选题库可见、下次编辑自愈，但不是事务。
- 冲突窗口是模块常量而非 `Config` 字段：客户端 fiber 没有配置管线；要改窗口需改代码，直到该常量移入配置。
- 日历条目跳选题库是降级的无参形态——打开选题库而非定位具体选题；带参跳转是本笔记继承的 topic-bank v2 后续项。
- 备注与排期同住 `_calendar.json`；用户手改该文件会产生孤儿备注，以命名问题浮出而非静默复活。

## Testing

`calendar.client.spec.ts` 钉住周网格、逾期规则、两条冲突规则、每个筛选维度、CSV 形态（BOM、CRLF、引号转义、备注合并）与整带回退的配置迁移；`content-schedule` 在既有 store 测试旁新增 `calendar-notes.spec.ts`（缺文件读取、未知版本与损坏结构拒载、逐条 problems、upsert/清除/时间戳行为），客户端整包套件——含 apply 装配与词典钉住测试——全部通过。
