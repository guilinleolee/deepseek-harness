# Agent Note：复盘视图导入平台指标导出、按账号基准判定优劣，并把结论回流产入选题库

状态：已实现

[English](2026-09-27-dsh-content-studio-review.md) | 中文

## 问题

【复盘】视图（v2 方案，`D:\dsh-content-studio\docs\review-dev-prompt-v2.md`）补上工作台的运营闭环：承接发布视图已登记的作品，导入各平台创作者中心的指标导出，渲染可对比的看板，对单作品做 AI 诊断，生成结构化周期报告，并把结论推回选题库。写代码之前有三件事钉死了设计：`.dsh-output.json` 零接触裁决（六个栏目共享其冻结 schema）、互动视图缺席（评论分析是延后的依赖，不是可以假装存在的 stub）、以及指标语义陷阱——各平台导出的口径互不一致：曝光不能跨平台求和，缺失的指标绝不能读成零。

## 决策

- **存储是主题级 sidecar 加隐身全局索引。** `outputs/<主题>/assets/_review.json`（`formatVersion 0`，拒载未知版本）承载基准线、快照与任务；`outputs/_review-index.json` 为历史列表镜像每个任务一行，与清单写入在同一提交序列内刷新，并有扫描重建兜底。删除移除任务及其报告文件，但保留全部快照与绑定——其他任务和看板还要复用。所有路径都经过 gather 面确立的纯文件名守卫。
- **导入是解析与提交两步，中间不落任何数据。** `parseReviewImport` 把一份 RFC 4180 CSV 按各平台的表头别名表映射（`标题（主）` 这类括号限定后缀会被归一化去除），`万`/`w` 后缀缩放到单位值，日期归一化为 UTC，返回解析行、带行号拒绝清单与未识别列；用户确认后 `commitReviewImport` 才把行落为快照。快照身份 = `平台 + 平台作品ID + UTC 日`：同日重复导入覆盖当日快照（幂等），更早的历史日永不改写——长尾识别完全依赖快照历史。未知列绝不静默丢弃——它们以勾选框呈现，选择会被记录。
- **只有绑定的行才进入分析池。** 快照的 `contentId` 非空才入池；绑定携带三级来源（`url` → `title` → `manual`，对齐 xhs-trail 的 `ContentSource` 形状），当前经 manual 面落地——自动匹配需要视图尚未读取的发布任务元数据，所以它是显式的后续项而非半接线的猜测。判定来自持久化的账号基准线：互动率达到基准两倍为爆款、低于一半为低表现；长尾只授予发布 ≥30 天、最近 7 天互动增速保持终身日均增速五分之一以上、且至少两个快照的作品。
- **AI 保持显式、排队、对失败诚实。** 两个调用（`analyzeReviewWork`、`generateReviewReport`）走共享 `streamLlmText` 助手与仅限限速的重试；报告提示词只收聚合摘要与带 500 字摘录的头部/垫底摘要——绝不收全文——并套用冻结的六节模板（受众反馈一节钉住占位文案，指明互动栏目缺席）。AI 调用失败仍然产出报告：客户端从聚合数据渲染纯数据版、落盘并把任务标为 `degraded`；磁盘写失败则正文留在编辑器、任务记为 `failed`。报告保存永远创建新文件，生成的原件永不被覆盖。
- **回流就是一次普通的选题库写入。** 一条建议变成一个 `TopicItemInput`（`source.type: "manual"`、标签 `复盘`），走既有 `contentTopics.put`；互动视图未来的 insights 供点是读取侧集成，在该视图上线前保持延后。

## 与方案文本的偏离

- 方案 M1 写的是 "CSV/Excel"；本期只交付 CSV 解析器。Excel 支持需要新的表格依赖，而方案自己的验收场景都以 CSV 为准——导入 UI 文案如实声明 CSV 范围。表头别名表以内置基线承载四个平台已知的导出列名（方案本身就把确切表头推迟到真实导出核对）。
- 方案在 UI 约定里写了 Chart.js；看板以工作台既有的卡片语言渲染分平台表格、排行列表与判定角标。今天没有任何栏目引入图表库，为一个视图把图表库拉进 bundle 是更差的交易——只有趋势图真正需要坐标轴时再议。
- 方案的绑定章节承诺导入时自动 `url`→`title` 匹配；多数导出形态里解析出的平台行不带作品 URL，自动匹配器需要发布任务的外链，故按上文延后。`matchMethod` 联合类型与逐快照来源字段已就位，匹配器落地无需改 schema。
- 方案的 MCP 章节冻结了 `fetchPlatformMetrics`；接口留在方案里，网关不保留方法——没有 provider 存在时，不留需要维护的死 RPC 面。

## 考虑过的替代方案

**把任务元数据写进 `.dsh-output.json`。** 直接否决：六栏目裁决冻结了该文件的 schema 抵御未知写入者，而复盘任务是横切记账，不是产出元数据。发布面冻结的 sidecar 模式就是同一个形状。

**报告调用改为服务端聚合。** 对标面已经定下模式：客户端计算聚合（看板渲染用的是同一组纯函数），AI 消化摘要。服务端聚合会用第二层实现重复指标语义，却换不来信任增益——网关本就校验每条存储快照的形状。

**新建 `contentReview` Remote 包。** 否决理由与 persona note 否决 `contentPersonas` 相同：十几个方法操作的文件与其他写面共享锁与原子写约定；content-outputs 是工作台唯一授权写路径。

## 后果

闭环可离线运转：导入、看板、基准线、绑定与纯数据版报告在无 LLM 时全部可用，每个落盘产物都不随浏览器更换而丢失。代价：枚举表与六节清单存在两份（客户端 `review/model.ts`、网关 `review/` 模块），一致性由测试钉住，新增平台必须双侧落地；自动绑定器缺席使未绑定作品暂时是手动粘贴 ID 的步骤，直到后续项落地；仅支持 CSV 意味着 Excel 用户需先另存。跨会话说明：发布、模板库与 notes 面在同包内并行演进；复盘面只增量触及共享组装点（`ContentStudio.tsx`、客户端 `index.ts`、`locales.ts`），回流复用 topics 面。
