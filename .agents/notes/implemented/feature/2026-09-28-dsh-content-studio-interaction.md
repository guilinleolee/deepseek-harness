# Agent Note: The interaction view opens a unified fan inbox over the library-root `_interactions.json` manifest, with hand-imported CSV as the only message source

Status: implemented

English | [中文](2026-09-28-dsh-content-studio-interaction.zh.md)

## Problem

The 【互动】 view (plan, `D:\dsh-content-studio\docs\interaction-dev-prompt-v1.md`, refreshed as v1.1) was the last unimplemented studio column: aggregate fan comments, DMs, and mentions from every platform into one inbox, draft AI replies that inherit the bound persona's tone, keep the conversation lifecycle explicit, and reflow audience insights into the topic bank. Three facts pinned the design before any code: the messages come from nowhere but a hand-run CSV import this phase (no platform API, no scraping, no automatic sending), the AI upstream rate-limits and runs out of quota as the normal case, and the frozen contract in the plan's chapter three had to land exactly — the v1 text itself forbids inventing mechanisms the code cannot see.

## Decision

- **Storage is one library-root system file.** `_interactions.json` (`formatVersion: 0`, reject-unknown) carries the conversations (messages embedded, `sentAt` ascending, newest conversation first), the AI-extracted insights, and a `summary` cache that the store recomputes on every read and write — the workbench badge reads it, no writer can drift it. One malformed conversation is dropped and named in `problems`; a bad envelope loads as empty with the rejection named; writes reject wholesale, the store never repairs. The file rides the same atomic-write lock as every other library-root entry, and `.dsh-output.json` plus the theme directories are never touched.
- **Import is parse-then-commit with the dedup and threading rules frozen in the parser.** The CSV contract is the plugin's own (exact header names, no alias table), UTF-8 only — text decoding with replacement characters rejects wholesale as a GBK export, no transcode guessing — capped at 5000 rows, partial-success per row with 1-based physical row numbers. Conversation identity is `platform + external_user_id`; message dedup is `platform + external_message_id` (a known id updates content and time in place, and a repeat inside one file collapses to the last row). Threading resolves `in_reply_to` against the library plus the batch and keeps unresolved parents as named warnings, never drops. The commit runs under the file lock so two importers cannot interleave.
- **AI stays explicit, queued, and per-call honest.** Three faces ride the shared `llm` Service Definition through the same stream/retry policy as every other column: reply drafts (fixed three candidates, persona digest and phrases as the tone base with the style parameter losing on conflict, an optional template-library skeleton framing the output), sentiment/intent classification (fifty messages per call, a garbled batch degrades to `unknown` instead of failing the loop), and insight extraction (two hundred per call, questions/pain points/interests, merged client-side by label with counts summed and `generatedAt` stamped once). All three charge the shared freemium quota — one generation per draft call, per fifty classified, per insight batch — and none block any local operation.
- **Sending archives locally and knocks on a locked door.** The send button appends an `out` message, flips `unread|pendingReply → replied`, and only then calls the reserved `sendInteractionReply` face — the always-failing `InteractionChannel` stub returns `MCP_NOT_CONFIGURED`, the toast says the reply was archived locally, and the status transition never depended on the call. The MCP pull entry renders disabled with the same wording the topic bank's AI placeholder uses.
- **The reflow is a plain topic-bank write with a new source family.** One insight line becomes one `TopicItemInput` with `source.type: "interaction"`, the conversation id as `refId`, and a create-time snapshot; the topic bank's source union gained the member (store validation, client table, filter, and locale label together), which the plan's 8.2 anticipated as the expected multi-source extension.

## Deviations from the plan text

- The plan's 二.2 mandated a new gateway package `@deepseek-ai/dsh-content-interactions` (the content-topics precedent). Not built: the review, publish, template, and persona faces all landed inside content-outputs as the single authorized write path — the review note rejected the same package split outright — and a separate package would have cut the AI/quota/lock sharing this face depends on. The plan's own method set was "minimal, adjust at implementation"; the shipped face is `readInteractions`/`writeInteractions`/`parseInteractionImport`/`commitInteractionImport`/`generateInteractionReply`/`classifyInteractions`/`extractInteractionInsights`/`sendInteractionReply`/`exportInteractionCsv`.
- The plan's 二.4 and 五.1 kept reply templates in a localStorage preset table because the template library did not exist when v1 was written. The library shipped that same day with an `interaction` category reserved, so the draft composer consumes the shared `TemplatePickerModal` (`category: 'interaction'`, rendered body as the generation skeleton) and the localStorage table is gone — recorded as v1.1 ruling 1 before implementation.
- The export CSV builder lives behind `exportInteractionCsv` rather than in the client: the import parser owns the format, so the round-trip guarantee is testable against the same module that enforces it. The client only aims the write (`writeAsset` into the chosen theme's `assets/`).
- Classification batches write the manifest after each batch (durable progress) while insight batches merge in memory and write once with the stamp; a failed classification batch leaves its messages `unknown` and the loop continues, a failed insight batch drops out of the merge and the final notice reports the partial failure.

## Alternatives considered

**A new `contentInteractions` package, as the plan originally froze.** Rejected for the reason the review note recorded: nine methods over files that share the library root, the write lock, and the AI policy with seven sibling faces; a second package would have duplicated the streaming/quota plumbing or forced cross-package internal imports the bundle purity gate forbids.

**Storing reply drafts outside the manifest.** Rejected: drafts are part of the message's history and must survive the browser; a sidecar per conversation multiplies files the scanner must stay blind to for no gain. The whole-manifest write the other faces already use covers drafts with the same wholesale validation.

**Auto-classifying at import time.** Rejected: the plan makes the two taggings explicit-button operations, quota is a real budget, and import must work fully offline. The unclassified placeholder (`unknown`, `source: "user"`, no `aiMeta`) renders nowhere, so nothing masquerades as a verdict.

## Consequences

The column closes offline: import, inbox, filters, tags, notes, stars, status moves, and the send-archive all work without an LLM, and every stored conversation survives browser changes because the truth is on disk. Costs: the enum tables exist twice (client `interaction-model.ts` mirrors the gateway tables, pinned by the parity test), a new platform must land in both plus the CSV column checks; the classification and insight loops charge the shared quota bucket, so a heavy inbox consumes the same daily budget as draft generation; and the plan's nav-side parametrized jump (第九章) landed in its documented degraded form — refs display as text, since `onNavigate(view, params)` still does not exist. Cross-session note: this face touched the shared assembly points (`ContentStudio.tsx`, client `index.ts`, `locales.ts`, the content-topics source union) additively while a sibling session was mid-flight on the competitor topic push; the template-store spec's stale fixtures were repaired by their own session between two reads and were not touched from here.
