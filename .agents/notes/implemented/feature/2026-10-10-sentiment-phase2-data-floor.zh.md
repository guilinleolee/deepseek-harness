# Agent Note: 舆情二期 —— RSS 数据底座、两级分类管线与告警聚合

Status: implemented

[English](2026-10-10-sentiment-phase2-data-floor.md) | 中文

## 问题

舆情栏目一期只交付了界面骨架：六个 Tab 全是硬编码演示行，每个按钮都是模拟 toast，什么都没落盘。2026-10-07 的调研早已定下架构——不做独立系统、沿用 GatherView 模式升级、一期数据源只做新闻 RSS（微博访客页与 B 站 wbi 留待后续期）、拒绝 5 分钟采集幻想——二期 ①–④ 要的正是让这些 Tab 变真的数据底座：可持久化的清单、真实采集、真实分类、带去重聚合的告警阈值。

## 决策

- **`_sentiment.json` 沿用画像清单的规则。** 输出库根部一个文件装下任务、提及、告警与设置（`formatVersion: 0`，无兼容承诺）。解析绝不隐藏坏记录：每条被丢弃的行都点名进 `problems`，每次写入都拒绝碰当前解析已丢记录的文件（`refusing to write`）——与画像 store 建立的 refuse-write 语义一致。
- **扫描引擎复用 gather 抓取器，而非另造一个。** `runSentimentScan` 通过 `fetchFeedDocument`（feedsmith 语法、条件请求游标、体积上限）抓取每个启用任务的 RSS 源，每个源最多取 30 条，按任务关键词组过滤（组内 AND、组间 OR；第一个命中的带极性组为分类加偏置），丢弃黑名单域名，存量上限 5000 条并按设置的保留窗口裁剪。单个不可达源跳过，扫描继续。
- **分类两级化是设计决定。** 第一级是本地词典（31 个负面词 + 20 个正面词）加基于命中差的置信度——免费、即时、对措辞强烈的文本已经够用。只有 `neu` 判定或置信度低于 0.7 才进第二级：一次批量 LLM 调用（每次扫描至多 12 条提及、`SENTIMENT_REFINE_PROMPT_VERSION = 'sentiment-refine@1'`、走已配置 AI 路由上的共享 `streamLlmText`），其 JSON 答案按序号解析；答案不可用时保留词典判定而非让扫描失败。AI 超时带独立原因码，UI 能点名。
- **告警按任务+日事件键聚合，等级由热度定。** 同一任务同一天的负面提及收敛为一条告警：热度优先取点赞/评论/转发之和，缺失时按条数乘 100；四级阶梯把热度与可配置的 `negativeHeatThreshold` 及其倍数比较。标记已处理是独立 Remote 面；webhook 推送本身留三期（设置表单现在保存配置并明示这一点）。
- **八个 Remote 面，一个网关对象。** `getSentiment` / `putSentimentTask` / `deleteSentimentTask`（级联删提及+告警）/ `setSentimentTaskEnabled` / `putSentimentSettings` / `scanSentiment`（单槽：并发调用立即拒绝）/ `handleSentimentAlert` / `sentimentStats`。快照带 `scanning` + `lastScan` 标志，UI 在扫描期间禁用按钮。客户端视图的每个 Tab 都从这些面渲染——看板的 14 天趋势与平台 TOP 榜来自 `sentimentStats`，明细行链接原文，报告 Tab 诚实标注 LLM 报告仍属二期后半。
- **⑤ 报告=框架化快照上的一次模型调用，失败降级为数据版模板（同日跟进切片）。** `generateSentimentReport` 把存量状态（统计摘要、任务名、平台分布、最新 10 条告警含已处理标记、最新 40 行提及含依据，12k 字符上限）框进固定五节提示词（`今日概览` / `负面舆情与风险点` / `正面声音与亮点` / `建议处置动作` / `明日关注清单`，`sentiment-report@1`）；模型任何失败都落确定性的降级模板而非报错——复盘栏的降级报告模式——清单只存最新一份（manifest 与 snapshot 的 `report` 字段）。报告 Tab 渲染存量 Markdown 并提供下载链接，降级报告显式标注可重试；快照的 `report` 随 `getSentiment` 下发，重生成=一次 Remote + 一次刷新。
- **⑥ 设置对"现在能存什么"保持诚实。** 设置表单补上账号黑名单文本域（与域名清单一同校验落盘；生效待社媒源落地），通知渠道各字段保存其配置并标注三期——延后的是 webhook 推送本身，不是存储。
- **告警→选题回流：一键一次 `topics.put`（三期第二件）。** 收件箱每行告警在"标记已处理"旁新增「转选题」动作：向选题库 upsert 一条——标题取所属任务名+告警简述、一句话取触发原因、`status: 'idea'`、`source: {type: 'manual'}`、标签 `舆情`、描述写明告警日期/风险等级/原因——走 gather 与复盘栏已在用的同一个注入式 `TopicBankGateway`。无新 Remote、无网关改动；舆情视图声明结构化的 `SentimentTopicsFace`（仅 `put`）让视图 spec 无需桩整个 topics 面，成败走视图既有通知通道。
- **三期首件·IM 推送：每次扫描每渠道一条汇总，尽力而为（跟进切片）。** 扫描把新告警落盘后，网关向每个已配置的 webhook 各发一条文本消息（钉钉与企业微信群机器人——两者都是公开的纯 JSON `{"msgtype":"text","text":{"content":…}}` 协议，无需 SDK）。汇总按严重度优先列出新告警（level 升序、同级取新）至多 5 行并附溢出指引回工作台；10 秒 POST 期限防止慢 IM 端点拖住扫描。设置的 `notifyEnabled` 总开关控制整轮，未配置的渠道不发，任何渠道失败只字符串化进控制台——告警已持久化，推送永远不能让扫描失败。邮件保持存而不发（SMTP 配置渠道尚不存在），设置表单补上总开关与如实说明这一点的文案。
- **声量对比：对标栏第四小节「声量对比」，零新后端（三期收尾件）。** 词行来自竞品账号赛道标签的并集（去重、去空、中文排序）；每个词的表格计数两侧——我的舆情提及中标题或摘要含该词的条数（客户端扫 `getSentiment`）与主题 `_competitors.json` 清单中标题含该词的作品数——全是两个栏目已拥有的数据，因此这是「一个可选注入读面（`sentimentRead: Pick<SentimentGateway, 'getSentiment' | 'sentimentStats'>`）+ 一个 React 小节」，无 Remote、无网关、无存储改动。小节每次进入取一次提及（切走/卸载即取消），每个空态如实指路：无舆情数据→先扫描；无赛道标签→去补账号标签；未注入面→小节自身隐藏。
- **数据源扩展：微博访客搜索 + B 站公开热搜，任务级勾选（三期后切片）。** `sentiment/sources.ts` 新增两个匿名适配器，读的都是平台自己的公开 web 端点——微博移动端容器搜索（`m.weibo.cn`，仅访客 cookie，不登录）与 B 站 nav 密钥的 wbi 签名热搜（每个 web 客户端都在跑的公开签名方案，密钥由 nav API 公开发放，无 SESSDATA；明确不碰 x-s/x-bogus 那条受保护反爬红线）。扫描循环改为按任务 `sources` 标志迭代：RSS 照旧，另对每个社媒源按任务第一个监控主体抓一页——主体搜索即检索过滤，社媒提及跳过 RSS 关键词组但走同一两级分类、域名黑名单，以及（本次起真正生效的）账号黑名单对作者的过滤。每个适配器在任何失败（HTTP、风控、网络）下降级为空页，被挡的源永远不能让扫描失败；任务对话框的数据源勾选框变为真实开关，过期的二期占位文案移除。
- **邮件渠道：推送轮的第三渠道，直接用设置块里的 SMTP 字段。** `pushEmail` 在收件人、主机、密码齐备时经 nodemailer 发一封汇总（465 隐式 TLS，其余 STARTTLS）——不另设服务端凭证文件，与 webhook 存 URL 同理：0600 清单就是凭证边界，同 `social-states/`。未配置或缺一项的渠道不发；传输失败与 webhook 一样字符串化进各渠道结果，绝不使扫描失败。设置表单新增主机/端口/账号/密码（掩码）/发件人字段，推送总开关继续统辖全部三渠道。

## 被否决的备选

**每条提及一次 LLM 调用。** 成本与延迟双重否决：关键词放宽时一个 30 条的源一次扫描就能开出几十次调用账单；词典预筛把模型账单压到至多一次批量调用，上限让最坏情况成为已知常数。

**按会话库模式建 SQLite 表。** 否决：本模块的数据是单用户可整读整写的清单，没有 JSON 边车服务不了的查询形态；画像与 gather store 已立下边车先例，工具链（文件锁、原子写、refuse-write）现成。

**网关内定时调度扫描。** 暂缓：扫描是手动优先（`立即扫描`），与 gather 的补偿式调度一致；定时调度器需要回答 gather 已解决过的"工作台开合"生命周期问题，`intervalMinutes` 现在就校验并落盘，调度器接上时无需迁移。

## 后果

代价：两部词典是人工维护的起点——LLM 级的存在恰恰因为词典覆盖不全，而一个"错误但自信"的词典判定（非中性且 ≥0.7）会跳过精析；扩充 `NEGATIVE_LEXICON` 是明示的维护面。仅 RSS 的覆盖意味着微博/B 站的议论在对应期落地前不可见；任务表单把数据源显示为固定项并附二期提示，而不是装作可采。验证：store spec（清单往返、refuse-write、任务 CRUD 级联、扫描去重 + 保留裁剪、词典与关键词匹配、批量解析、告警聚合分级、统计）加报告 spec（框架上限、降级回退溯源、最新报告存储）与重写的视图 spec（桩网关上的 10 个 jsdom 测试：Tab 渲染真实行、对话框保存/启停往返、带插值条数的扫描通知、告警处理、设置保存、加载失败提示、报告生成与下载链接、降级报告标注），双包 52 文件 / 625 测试全绿，oxlint 双包 0 错误，typert 工件已再生，:3080 在发 bundle 已核验携带含 `generateSentimentReport` 在内的全部九个面。
