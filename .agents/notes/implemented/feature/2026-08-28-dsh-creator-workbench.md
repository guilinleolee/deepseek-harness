# Agent Note: `@deepseek-ai/dsh-creator-workbench` ships as a SOP-driven, no-API-publish self-media workstation

Status: implemented

English | [中文](2026-08-28-dsh-creator-workbench.zh.md)

## Problem

A self-media creator needs a workspace that ties four stages — topic planning, script drafting, quality gating, multi-platform export — to a single conversation surface, but the obvious platform-API path is blocked. WeChat, Xiaohongshu, Douyin, Toutiao, Zhihu, and Bilibili either offer no stable publication API or one with severe quota, throttling, and IP-whitelisting limits; the "five tools, one integration adapter per platform" pattern the development plan originally proposed therefore cannot ship as a usable workflow.

The second problem is repeated-recipe reuse. The Tianlong Engine (`C:\Users\li\.claude\projects\dragon-engine\skills`) already ships 200+ skills covering XHS visual direction (`xhs-visual-director`), Bingling brand assets (`lib-bingling-v2`), intelligent illustration (`shibazi-illustrator`), and WeChat article fetching (`wechat-skills-unified`). Re-implementing these inside a new workbench is wasted work, but naively shelling out to those scripts from the workbench would couple the DSH plugin to a non-deterministic external runtime and break the "what you see is what the SOP reads" promise.

## Decision

The package ships as a SOP-driven composition rather than a tool-driven one. The agent spine consumes an authoritative `sop/creator-workflow.md` (six stages: scout → plan → write → gate → export → review) loaded through the model's own `read_file` tool, and the persona in `cordis.yml` only identifies the role. Editing the SOP never binds to `SESSION_FORMAT_VERSION=0` because the model pulls it from disk on every turn instead of having it embedded in the system prompt. Six platform templates under `prompts/platforms/{wechat,xiaohongshu,douyin,toutiao,zhihu,bilibili}.md` plus a `prompts/style/style-dna.md` brand-DNA file provide the writing surface; the `QualityGate SOP` documents — `gate-{grammar,factual,compliance,tone,structure}.md` — drive the gate fan-out, and a Python `run_gate.py` runs the deterministic gates (grammar, structure, compliance) while a subagent agent handles the model-driven ones (factual, tone).

Five shell scripts under `scripts/` are the package's only side-effect surface: `scan_inputs.ps1` for material inventory, `run_gate.py` for gate execution, `illustrate.ps1` for image generation, `export_content.ps1` for the multi-platform transform, and `sop/creator-workflow.md` for the procedure itself. Every output is a copy-paste artifact under `$CREATOR_WORKBENCH_OUTPUT_DIR`; the package never invokes a platform publication API. Approval happens once at export time through `ctx.userApproval.request`, and per-platform failures degrade to `export_errors.json` without aborting the run.

The cordis overlay is a single `- insert:` patch on top of `dsh-base` (the user runs `dsh web --patch "$(node -p 'require.resolve("@deepseek-ai/dsh-creator-workbench/cordis.yml")')"`); same-id rows replace dsh-base defaults (the agent spine persona, the bash + fs-local cwd), and new rows add workbench-only capabilities (`subagent-spawn-in-process`, `tool-subagent`, `workflow-worker-thread`, `tool-workflow`, `tool-ralph`, `skill-filesystem`, `tool-skill`, `web` + `web-search-deepseek`, `tool-web`).

The Tianlong Engine is wired through `dsh-skill-filesystem` with `paths: [process.env.CREATOR_WORKBENCH_SKILLS_PATH ?? 'C:\\Users\\li\\.claude\\projects\\dragon-engine\\skills']`, so the agent can read skill SKILL.md files as model-facing reference material but never executes the underlying scripts. The shibazi-illustrator HTML engine, however, ships with a `main()` gate that depends on `import.meta.url === file://${process.argv[1]}`; some `npx bun` invocations on Windows break that equality, so the CLI exits 0 without ever running `main()`. `scripts/illustrate.ps1` detects the empty output and falls back to a built-in HTML card so exports never block on art.

## Alternatives considered

**A platform-adapter pattern with one driver per platform.** It mirrors the standard "publish everywhere" UX, but every adapter was a research project of its own (signing flows, IP whitelisting, rate limit recovery), and the published result would be a non-functional demo until a year of integration work shipped. Replaced by the deterministic transform model after WeChat draft-box API confirmation, Xiaohongshu & Douyin API absence, and Bilibili quota policy all converged on "no stable publication path". The current copy-paste export requires the user to do the last 30 seconds of work, but those 30 seconds actually publish.

**Spawning the Tianlong Engine scripts directly from the workbench (subprocess).** The visual quality of the Tianlong outputs is the reason this workbench exists at all, and a direct subprocess call would have been the shortest path. Rejected because (a) the scripts run external state machines (Playwright, Chrome) that the DSH sandbox cannot observe, (b) the Tianlong version pin is not the DSH release contract, and (c) every execution would re-resolve credentials and taint the model-visible transcript. Reading the SKILL.md files as model input is the same total information the user would have gotten by reading the docs once, and the model is free to act on it without a side channel.

**One Cordis plugin per workbench stage (plan-topics, write-draft, run-pipeline, publish-content, fetch-analytics).** Five model-facing tools mapped one-to-one to the SOP stages. Rejected because the workbench does not need them: every model-facing operation is already a `bash` invocation of a CLI script plus a `read_file` for the SOP. Adding new model-facing tools is also a SESSION_FORMAT commitment; reusing the DSH base tools keeps the conversation transcript stable across SOP edits and platform additions.

## Consequences

The package is no-runtime-invariant: it contributes exactly one `agentInstructions.register` call from `apply()` and no Cordis service. The `./invariant` companion declares this; downstream invariant gates stop looking for a state machine. Three consequences follow. First, every SOP edit ships without re-publishing: the model re-reads `sop/creator-workflow.md` on every turn, so a typo fix or a new platform does not require a session-log bump. Second, the CLI scripts (`run_gate.py`, `export_content.ps1`, `illustrate.ps1`) are the only side-effect surface; testing them in isolation is straightforward and `examples/creator-workbench/tests/package.spec.ts` (6 tests) + `cordis-overlay.spec.ts` (1 test) lock the SOP, prompt templates, and overlay shape. Third, the Tianlong Engine becomes a runtime-independent reference, not a deployment dependency; a contributor can develop the workbench on a machine without Playwright or Chrome, and CI does not need the engine installed.

Two real costs. The shibazi-illustrator fallback means the WeChat richtext may ship without a perfect card on a fresh export, and the user has to refresh the illustration by hand. The platform copy-paste model means the workbench is a productivity multiplier, not a "click publish and walk away" tool — a tradeoff the platform-API surface rules out anyway. The package's known-limitations section records both.
