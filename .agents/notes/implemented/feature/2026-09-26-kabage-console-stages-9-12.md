# Agent Note: 卡巴格管理台阶段 9-12 — 工具 RBAC、个人中心与邀请、TOTP/邮件/SSO、管理工具挂平台

Status: implemented

[English](2026-09-26-kabage-console-stages-9-12.md) | [中文](2026-09-26-kabage-console-stages-9-12.zh.md)

## Problem

Blueprint phases 9-12 (`卡巴格管理台栏目规划v2.md` §7) close four capability gaps left after the security/audit/quota phases: (1) an instance's agent could freely use command-line, filesystem, and network tools with no role-based control; (2) employees had no self-service surface — password resets, quota checks, and device revocation all required an admin; (3) no second factor, no outbound notification, no enterprise SSO; (4) a DSH agent could not manage the platform itself (the original plan's `user:*` tool list). All four phases land on the established platform: zero-dependency Node ESM, `data/*.json` stores, one daemon hosting gateway + relay + console + supervisor loops, one DSH instance per employee.

## Decision

**Phase 9 — instance-level tool RBAC.** One person = one instance, so policy is per instance: `data/toolpolicy.json` maps each role to denied tool groups (`command` = bash/pwsh/terminal_*, `fs` = read/write/edit/glob/grep/str_replace_editor/read_image, `network` = web_search/web_fetch; anything else passes). The console endpoint and the departments-&-roles page write policy changes straight into each bound instance home as `<home>/tool-policy.json` — hot-reloaded by the plugin via an mtime+size cache, no restart. `platform/plugins/kabage-tool-guard/` registers a global `ctx.tools.guard()` (verified contract: returning a string denies with `Error: <reason>`, guards have no allow power; an exception fails only the call at hand). Missing policy file = allow (an admin instance may legitimately have none); present-but-invalid = fail-loud. Denials append to `<home>/guard-events.jsonl`; the supervisor's existing disk sampler transcribes new lines into the platform audit log as `guard.deny` events every 30s, truncating only when the file fingerprint (mtime+size) is unchanged.

**Phase 10 — personal center + invite registration.** `/me` on the portal host serves employees (auto-redirect after login; admins/auditors may use it too): profile, password change (policy-checked, then token epoch bump signs out all devices), own month-to-date points usage (points/legacy/unlimited renders), last 5 logins from the audit log (exact-match filter), and revoke-all-devices. Invites store only the SHA-256 of a 192-bit code; registration validates with timing-safe comparison, rejects used/expired/revoked with stable reason codes, creates the account through the same `addAccount` path (whitelist + password policy + scrypt), issues the virtual key, syncs the instance tool policy, and consumes the invite only on success — failures never burn the code. The public register endpoint shares the login rate limiter's parameters in a separate per-IP bucket.

**Phase 11 — TOTP, mail, SSO.** `totp.mjs` implements RFC 4648 base32 and RFC 6238 (HMAC-SHA1, 30s step, ±1 window), accepted against the RFC's own appendix-B vectors. Secrets are stored AES-256-GCM-encrypted (key derived from the existing `auth-secret.key`); login becomes two-step — correct password yields `{totp_required:true}` with no cookie, then `POST /api/auth/totp` issues the session. TOTP failures share the login rate-limit bucket, and a correct password does **not** reset the failure counter (a password thief cannot brute-force codes indefinitely). A corrupted ciphertext record is **fail-closed**: login is refused with a rescue message, a `security.twofa_broken` audit event fires, and the admin-side reset button is the recovery path. `require2faRoles` in security settings is a soft nudge (banner), not a hard lock — locking out the last admin is worse than a delayed enrollment. Mail supports `off`/`file`/`smtp` (hand-rolled minimal client: multiline EHLO, STARTTLS only when advertised, AUTH LOGIN, response-code whitelist, CRLF injection rejected at config-save); quota warnings fire once per account per month at 80% (booked inside the usage mutex), account-change notices never contain password material, and send failures resolve instead of rejecting so the relay path can never crash on them. SSO ships WeCom and DingTalk OAuth adapters driven entirely by `data/sso.json` (secrets GCM-encrypted, `authorizeBase`/`apiBase` configurable): one-time state, 10s fetch timeouts, state-map cap with 429 overflow, binding through a password-verified page inside `withAccountLock`, and denial of login for non-enabled providers.

**Phase 12 — platform admin tools for DSH agents.** `data/service-tokens.json` stores SHA-256 hashes of `kbsvc-…` bearer tokens in two roles (admin, readonly — readonly is a precise-path Set whitelist over read-only APIs, default-deny, with deny-audit); revocation takes effect on the next request via mtime cache; audit actors are recorded as `svc:<name>`. `platform/plugins/kabage-admin-tools/` registers seven tools (list/quota-query/audit-query read-only; create/update/reset-password/disable mutating) that call the console API over HTTP with explicit `inject:['tools']`, `presentCall` generic presentation, `encodeURIComponent` on every dynamic parameter, `exec.signal` propagation, result truncation at 50 rows, and Chinese error translation of 401/403/4xx/network failures. One-time passwords returned by create/reset carry an explicit change-it-now notice and the README warns that admin-instance session logs will contain them. The e01 env block reserves `KABAGE_SERVICE_TOKEN` (empty placeholder; a real token is generated by CLI and pasted by the admin — the plugin reports `token_missing` in Chinese rather than sending an empty credential).

**Review-driven hardening** (three adversarial passes across phases 9-12, probes included): unsafe-key rejection at write/normalize/resolve layers, quote-escaping in `esc()`, disconnect-refund with a single `settled` flag, strict pre-deduct accounting, register-queue guaranteed responses, exact-match audit filtering, fingerprint-guarded transcription truncation, the TOTP fail-closed above, SSO timeouts/caps/locking, SMTP response-code whitelist plus converting send failures from rejects to resolved results (a latent unhandled-rejection crash), and per-dataDir service-token caching.

## Alternatives considered

**Approval-group enforcement in phase 9** (an `approval` list alongside `deny`). Deferred: the guard contract only denies, and routing approvals through `ctx.approval` needs instance-side plumbing that deserves its own slice — the field is carried in the policy schema so enabling it later is additive.

**Hard-enforcing 2FA enrollment** (`require2faRoles` blocking login). Rejected: a stale secret or lost authenticator would lock out the last admin with no self-service recovery; soft nudge + admin-side reset keeps rescue possible.

**Failing open on TOTP ciphertext decryption** (the first implementation treated decrypt failure as "not enrolled"). Rejected after review: key rotation or file corruption would silently downgrade enabled accounts to single-factor, leave `enabled:true` stuck (no self-re-enrollment), and write nothing to the audit log. Fail-closed with an explicit rescue path costs one extra state and removes all three.

**Registering mutation tools conditionally based on token role.** Rejected: it couples tool registration to probing the token's authority at startup; instead all tools register and the platform's 403 is translated into a Chinese tool error — one source of truth for authorization.

**Waiting for real WeCom/DingTalk credentials before shipping SSO.** Rejected: both adapters are fully driven by configuration with configurable API bases, so a local mock OAuth server exercises the entire authorize→callback→bind→direct-login flow; real credentials drop in as config, not code.

## Consequences

Verified in the worktree with zero dependencies across eleven suites, 575 assertions total (43+40+32+85+63+55+47+24+26+58+42), including real-HTTP gateway flows against mock upstreams/providers/SMTP peers; both plugins additionally passed a real `precheck` boot (isolated home, pnpm install, plugin loaded and registered, health 200 — 35s and 42s). Three adversarial review rounds ended with no P0s; all five P1s and the tractable P2s were fixed with assertions before commit.

Deferred, known: real-TOTP-code replay within its window (no last-used counter yet, ~90s upper bound); no account-global rate-limit bucket (per account+IP buckets scale linearly with attacker IPs); `require2faRoles` hard enforcement; guard `approval` groups; real external SMTP and real WeCom/DingTalk end-to-end (both config-gated and mock-verified); the real LLM agent tool-call chain (needs a funded upstream — deployment path is ready: `add-service-token`, fill e01 env, `plugin-push`, activate). Operational notes: deploy must keep the production `instances.json` (gateway `0.0.0.0`) and merge the e01 env placeholder; plugin push from this sandbox has historically failed under load — the exact CLI commands are in the platform README if manual execution is needed.
