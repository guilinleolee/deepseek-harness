# Agent Note: 画像向导第一步获得自有站点证据块——向导抓取用户的博客或企业官网并从中提取画像字段

Status: implemented

[English](2026-10-03-persona-own-site-extraction.md) | 中文

## 问题

画像表单在 wire 上早已携带 `site.url` 与 `site.pastedText`，`buildFactsText` 也早已把粘贴文本送进报告事实——但输入框躺在第 2 步的社媒链接之间，解析按钮是禁用占位（"网页抓取后续版本开放"）。拥有博客或企业官网的用户没法让分析读到自己的站点：只能把网站已经写明的内容再抄一遍。

## 决策

- **站点块放在第 1 步，与简历块并列。** 两者都是"我是谁"的证据——一份私人简历与一个公开站点——而第 2 步保持纯社媒链接。没有 wire 字段移动；动的只是 DOM 与文案（`企业官网` → `官网 / 博客`，因为该字段同样服务个人博客）。
- **一个新 AI 操作 `site` 在网关内完成抓取与提取。** `persona/site.ts` 规范化用户输入的地址（无协议输入补 `https://`；仅 http(s) 通过，`file:`/`data:`/`javascript:` 在构建请求前即被拒绝），以声明的 User Agent、30 秒截止与 2 MiB 上限抓取，剥掉 `<head>`，并经共享的 gather 净化器把正文还原为可见文本。`PersonaAiProcessor` 新增 `site` 分支：先抓取，再做一次提取调用，其 JSON 契约与简历面一致（`persona-site@1`；与通用补全不同，`whoAmI` 允许出现）。抓取与模型调用共用单槽队列与限流重试；抓取失败不重试。
- **抓取文本被持久化，而非一次性消费。** 结果把抓取文本带回；控制器将其写入粘贴文本域（按 wire 的 100 k 截断），于是保存的表单、报告事实（新增 `官网 / 博客` URL 行；粘贴行改标 `官网内容`）与后续全部分析读的是同一份内容。抓取结果为空时不返回 `text`，用户粘贴的备用文本得以保留。无网址时粘贴文本按原样分析——文本域兼任需要登录的站点的备用入口。
- **采纳路径沿用现有机制。** 候选值进入共享的补全预览面板（`origin: 'site'`），仅在采纳后才落进表单；任何 AI 生成内容都不隐式进入保存路径。不设知情同意门：被分析的是用户指向的公开页面，不同于简历的个人数据。

## 被否决的备选

**拆成两个 Remote（`fetchSiteText` + 接收文本的 AI 操作），像 gather 面的切分。** 否决：画像面是每次点击一个显式按钮，拆开将迫使客户端串接两次调用、把抓取文本放进临时状态，并区分抓取失败与 AI 失败——而两者本来就会汇成同一条提示。

**`report` 操作在设置 `site.url` 时自行抓取。** 否决：报告将获得网络依赖与逐次生成的非确定性，重新生成可能悄悄改变用户已读过的结论。持久化文本路线让报告确定性地读到同样内容。

## 后果

代价：网关现在会代用户输入的 URL 发起出站请求——与 gather 面的订阅源 URL 同一信任级别（本地用户自己的工具），由协议校验、截止时间与大小上限守护。`htmlToText` 会把段落压成一大块文本，提取提示词可以容忍（gather 面带着同样的取舍已上线）。验证：两个包共 53 个测试（抓取/规范化用例、`site` 操作、控制器流、第 1 步视图接线），两包类型检查干净，触及文件 oxlint 干净。
