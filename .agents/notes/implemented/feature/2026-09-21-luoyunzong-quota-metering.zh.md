# Agent Note：落云宗月度 Token 配额以 Relay 每请求检查硬停，用量抽取带缓冲上限

Status: implemented

[English](2026-09-21-luoyunzong-quota-metering.md) | 中文

## 问题

任务书阶段 4：按人月度 Token 额度、硬停语义（决定 2）、按部署服务器本地时区重置（决定 6）、执行点在 Relay——验收两条：实例内篡改本地状态不影响拦截；超限错误对员工可读。Relay 从阶段 3 起就拥有每请求检查点（虚拟钥匙认证、模型授权），悬而未决的是：不信任实例的前提下用量怎么计量、正好压线的硬停行为如何、以及在手头上游全部无余额（只回 429、无 usage 载荷）时计量路径怎么验证。

## 决策

配额强制并入 Relay 既有每请求链：虚拟钥匙认证 → 模型授权 → 月度额度 → 转发。账号可设 `monthlyTokens`（不设 = 不限，如管理员；`0` = 立即停）；当月用量（`tokensIn + tokensOut`）到线即拒新请求，返回可读的 OpenAI 形 429（`insufficient_quota`，中文提示「本月 Token 额度已用完（已用/额度）…」）。用量在服务端计量：Relay 对每个上游响应做 tee——SSE 逐行扫末块 usage 对象，JSON 整体缓冲（8 MiB 抽取上限）——按服务器本地时区的 `YYYY-MM` 月键记入 `data/usage.json` 的 `{tokensIn, tokensOut, requests}`（单进程内 promise 链互斥串行读改写 + 原子替换）。流式请求自动注入 `stream_options: {include_usage: true}`（调用方已带则不覆盖），合规上游即会在末块报 usage。计量失败只降级精度（少记），绝不阻塞请求。`set-quota` 写入的账号文件网关与 Relay 本来就每请求按 mtime 重读，改额度下一请求即生效；`list-usage` 渲染每账号 已用/额度/剩余。

验证用受控 mock 上游（30 行夹具服务，按普通上游注册、事后移除）让真实 Relay 路径——认证、白名单、配额、转发、抽取——端到端跑通：非流式 JSON 与流式 SSE 的 usage 均正确入账（admin 两种模式各 +100/+20）；500 额度的 member 打 120 token 的模型五次全过（120→600），第六次硬停于可读的 600/500 错误；`--tokens 0` 的账号持完全有效的钥匙也被立即拒——证明执行点是服务端计数器，即实例本地状态按构造不可能影响拦截。月键对照本地时间确认（`2026-09`）；跨月滚动由月键分离按构造成立。

## 已否决的替代方案

**按请求数配额。** 否决：截图语义（以及模型与权限页的分向计价列）是 token 制；Relay 已分开记录 `tokensIn`/`tokensOut`，后续控制台计价层可直接乘倍率，无需改表。

**信任实例侧计量。** 直接否决——任务书的安全原则（「服务端强制，不信任实例自律」）正是为「实例内跑着任意 agent 代码」而写；计数器只存在于 Relay 的 data 目录。

**到线时掐断 in-flight 请求。** 决策 2 的语义已否决：检查在请求准入时做，已转发的请求跑完。这也让实现天然无竞态——准入检查只读已提交的用量。

**现在就做计价倍率。** 推迟：计费展示属控制台；计量表已分向，倍率来了不改结构。

## 后果

阶段 4 验收在无余额条件下全部成立，硬停环路端到端实测（五次 200 后一次可读 429 于 600/500；额度 0 的账号即刻被停）。代价与遗留：Relay 崩溃只会丢最后未提交的一笔用量（MVP 规模可接受，控制面数据库会做成事务）；上游 `prompt_tokens_details` 的缓存读/写 token 类别尚未拆分（计价倍率会需要）；跨月滚动是月键构造成立而非跨月实测。另外，压测暴露并修复了阶段 1 一个值得点名的潜伏缺陷：磁盘占用采样每 60 秒同步遍历 pnpm 重度的实例 home，把事件循环饿死数十秒——请求只能在遍历间隙被服务。遍历已改异步（`fs/promises`），间隔 120 秒。
