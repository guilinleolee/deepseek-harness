# Agent Note: Sentiment phase 2 — the RSS data floor, the two-stage classify pipeline, and alert aggregation

Status: implemented

English | [中文](2026-10-10-sentiment-phase2-data-floor.zh.md)

## Problem

The sentiment view shipped as phase-1 UI chrome: six tabs over hardcoded demo rows, every button a simulated toast, nothing persisted. The 2026-10-07 research had already fixed the architecture — no standalone system, the GatherView pattern upgraded, news RSS as the only phase-2 source (weibo visitor pages and bilibili wbi APIs stay later-phase), no five-minute collection fantasy — and phase 2 ①–④ asked for the data floor that makes the tabs real: a persisted manifest, a real collector, real classification, and alert thresholds with deduplicated aggregation.

## Decision

- **`_sentiment.json` follows the persona manifest rules.** One file at the outputs-library root holds tasks, mentions, alerts, and settings (`formatVersion: 0`, no compatibility promise). Parsing never hides a bad record: every dropped row is named in `problems`, and every write refuses to touch a file whose current parse dropped records (`refusing to write`) — the same refuse-write semantics the persona store established.
- **The scan engine reuses the gather fetcher, not a new one.** `runSentimentScan` fetches each enabled task's RSS feeds through `fetchFeedDocument` (feedsmith grammar, conditional-request cursors, size caps), takes at most 30 entries per feed, filters by the task's keyword groups (AND within a group, OR across groups; the first matching polarized group biases classification), drops blacklisted domains, and caps stored mentions at 5,000 with a settings-driven retention prune. One unreachable feed is skipped; the scan continues.
- **Classification is two-stage by design.** Stage 1 is a local lexicon (31 negative + 20 positive terms) with margin-based confidence — free, instant, and enough for strongly-worded text. Only `neu` verdicts or confidence below 0.7 go to stage 2: one batched LLM call (at most 12 mentions per scan, `SENTIMENT_REFINE_PROMPT_VERSION = 'sentiment-refine@1'`, streaming through the shared `streamLlmText` on the configured AI route) whose JSON answer is parsed per-index; an unusable answer leaves the lexicon verdicts in place rather than failing the scan. The AI timeout carries its own reason code so the UI can name it.
- **Alerts aggregate per task+day event key, level from heat.** Negative mentions of one task on one day collapse onto one alert row: heat is the summed likes/comments/shares when present, else the count times 100; the level ladder (1–4) compares that heat against the configurable `negativeHeatThreshold` and its multiples. Marking handled is its own Remote face; the webhook push itself stays phase 3 (the settings form saves the config now and says so).
- **Eight Remote faces, one gateway object.** `getSentiment` / `putSentimentTask` / `deleteSentimentTask` (cascades mentions+alerts) / `setSentimentTaskEnabled` / `putSentimentSettings` / `scanSentiment` (single-slot: a concurrent call rejects immediately) / `handleSentimentAlert` / `sentimentStats`. The snapshot carries `scanning` + `lastScan` flags so the UI disables the button during a run. The client view renders every tab from these faces — the dashboard's 14-day trend and platform top list come from `sentimentStats`, the mention rows link to the original articles, and the report tab honestly states the LLM report is still phase 2½.
- **⑤ The report is one model call over the framed snapshot with a data-only fallback (same change, follow-up slice).** `generateSentimentReport` frames the stored state (stats summary, task names, platform spread, newest 10 alerts with handled markers, newest 40 mention lines with evidence, 12k-char cap) into a fixed five-section prompt (`今日概览` / `负面舆情与风险点` / `正面声音与亮点` / `建议处置动作` / `明日关注清单`, `sentiment-report@1`); any model failure lands the deterministic degraded template instead of an error — the review column's degraded-report pattern — and the manifest stores the newest report only (`report` field on the manifest and snapshot). The report tab renders the stored markdown with a Markdown download link and names degraded reports for retry; the snapshot's `report` rides `getSentiment`, so regeneration is one Remote and one refresh.
- **⑥ Settings stay honest about what saves now.** The settings form gained the account-blacklist textarea (stored and validated alongside the domain list; enforcement applies once social sources land), and every notification-channel field saves its configuration with phase-3 copy — the webhook push itself is the deferred piece, not the storage.
- **Alert→topic reflow: one click, one `topics.put` (phase-3 second slice).** Every alert row in the inbox now carries a 转选题 action beside mark-handled: it upserts one topic-bank item — title from the owning task name plus the alert summary, one-liner from the trigger reason, `status: 'idea'`, `source: {type: 'manual'}`, the tag `舆情`, and a description naming the alert's date, risk level, and reason — through the same injected `TopicBankGateway` the gather and review columns already ride. No new Remote, no gateway change; the sentiment view declares a structural `SentimentTopicsFace` (`put` only) so the view spec stubs it without the whole topics surface, and success/failure surface through the view's existing notice channel.
- **③-of-phase-3 IM push: one digest per channel per scan, best-effort by design (follow-up slice).** After a scan persists its new alerts, the gateway posts one text message to every configured webhook (Dingtalk and WeCom group robots — both public plain-JSON `{"msgtype":"text","text":{"content":…}}` protocols, no SDK). The digest lists the new alerts severity-first (level ascending, newest tiebreak) capped at 5 lines plus an overflow pointer to the workbench; a 10 s POST deadline keeps a slow IM endpoint from pinning the scan. `notifyEnabled` on the settings gates the whole round, unconfigured channels fire nothing, and any channel failure only stringifies into a console error — the alerts are already persisted, so push can never fail the scan. Email stays stored-but-dormant (an SMTP-configured channel does not exist yet), and the settings form gained the master switch plus copy that states exactly this.
- **Volume compare: a fourth 声量对比 section in the competitors view, zero new backends (phase-3 closing slice).** The word rows come from the union of the rival accounts' niche tags (deduped, blank-dropped, zh-collated); for each word the table counts my sentiment mentions whose title or summary contains it (a client-side scan over `getSentiment`) and the works in the theme's `_competitors.json` manifest whose title contains it — both sides are data the two columns already own, so this is one optional injected read face (`sentimentRead: Pick<SentimentGateway, 'getSentiment' | 'sentimentStats'>`) and a React section, no Remote, no gateway, no store change. The section fetches mentions once per visit (cancelled on unmount/tab change), and every empty state names its next action honestly: no sentiment data → scan first; no niche tags → tag the accounts; no face injected → the block itself hidden.
- **Source expansion: weibo visitor search + bilibili public hot search, per-task toggles (post-phase-3 slice).** `sentiment/sources.ts` adds two anonymous adapters over the platforms' own public web endpoints — weibo's mobile container search (`m.weibo.cn`, visitor cookies only, no login) and bilibili's nav-keyed wbi-signed hot search (the open signing scheme every web client runs; keys served publicly by the nav API, no SESSDATA, and explicitly NOT the protected x-s/x-bogus anti-bot line). The scan loop now iterates the task's `sources` flags: RSS as before, plus one search page per social source on the task's first subject — the subject search is the retrieval filter, so social mentions skip the RSS keyword groups but run the same two-stage classification, domain blacklist, and (newly live) the account blacklist against the author. Every adapter degrades to an empty page on any failure (HTTP, gate, network), so a blocked source can never fail the scan; the task dialog's source checkboxes are now real toggles and the stale phase-2 copy is gone.
- **Email channel: the push round's third channel over the settings' own SMTP fields.** `pushEmail` sends one digest via nodemailer (implicit TLS on 465, STARTTLS otherwise) whenever the recipient, host, and password are all set in the same `_sentiment.json` settings block — no separate server-side credential file, matching how the webhooks already store their URLs; the 0600 manifest is the credential boundary, same as `social-states/`. Unconfigured or partially configured channels send nothing; transport failures stringify into the same per-channel outcome as the webhooks and never fail the scan. The settings form gained host/port/user/password (masked)/sender fields, and the push switch continues to gate all three channels.

## Alternatives considered

**An LLM call per mention.** Rejected on cost and latency: a 30-entry feed with loose keywords could bill dozens of calls per scan; the lexicon prefilter keeps the model bill to at most one batched call, and the cap makes the worst case a known constant.

**A SQLite table per the session store.** Rejected: the module's data is one user-facing manifest, read-modify-written whole, with no query patterns a JSON sidecar cannot serve; the persona and gather stores set the sidecar precedent and the tooling (file lock, atomic write, refuse-write) already exists.

**Scheduling the scan on a timer inside the gateway.** Deferred: the scan is manual-first (`立即扫描`) exactly like the gather catch-up; an interval-driven scheduler needs the same "workbench open" lifecycle answers gather already had to solve, and `intervalMinutes` is validated and stored now so the scheduler consumes it without a migration.

## Consequences

Costs: the lexicons are hand-curated starting points — the LLM stage exists precisely because lexicon coverage is incomplete, and a wrong-but-confident lexicon verdict (≥0.7 non-neutral) skips refinement; widening `NEGATIVE_LEXICON` is acknowledged maintenance. RSS-only coverage means weibo/bili chatter is invisible until their phase lands; the task form shows the sources as fixed with a phase-2 hint instead of pretending. Verification: the store spec (manifest round-trip, refuse-write, task CRUD cascade, scan dedupe + retention prune, lexicon and keyword matching, batch parse, alert aggregation levels, stats) plus the report spec (framing caps, degraded fallback provenance, newest-report storage) and the rewritten view spec (10 jsdom tests over a stubbed gateway: tabs render live rows, dialog save/toggle round-trip, scan notice with interpolated count, alert handling, settings save, load-failure notice, report generation with download link, degraded-report flag), 52 files / 625 tests green across both packages, oxlint 0/0 on both, typert artifacts regenerated, and the served :3080 bundle verified to carry all nine faces including `generateSentimentReport`.
