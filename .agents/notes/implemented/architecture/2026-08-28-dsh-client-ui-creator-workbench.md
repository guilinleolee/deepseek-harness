# Agent Note: `@deepseek-ai/dsh-client-ui-creator-workbench` ships as a dependency-free three-column tab using the existing DSH slot system

Status: implemented

English | [中文](2026-08-28-dsh-client-ui-creator-workbench.zh.md)

## Problem

The Creator Workbench has a host half (`@deepseek-ai/dsh-creator-workbench`) that drives a SOP across the standard DSH conversation, but creators working on long drafts want a dedicated three-column view (file tree / Markdown editor / pipeline status) that lives next to the chat drawer rather than replacing it. The DSH web shell already has a slot-based UI composition system; the question is what a workbench tab registers into, and what its components read.

The naive answer is a full DSH-aware client package that depends on the runtime, the conversation package, the slots package, the layout package, and a state library. The constraint set has only three real needs: a file tree (state: selected path, expanded set), an editor (state: open documents, active path, dirty flag), and a pipeline panel (state: five stage statuses). The "third-party state library" answer turns one file of state into two new packages of maintenance; the "import every DSH client primitive" answer makes the workbench depend on icons and button primitives it does not use, just to keep the bundle shape consistent.

## Decision

The browser half ships as `@deepseek-ai/dsh-client-ui-creator-workbench`, a self-contained DSH client plugin that contributes exactly one top-level tab. The package's only state management is a 60-line `stores.ts` that defines `getState` / `subscribe` / `actions` on three small bundles — file tree, editor, pipeline — and binds them to React 18's built-in `useSyncExternalStore` via a one-line `useStoreState` hook. No `zustand`, no `Redux`, no observable library; the `React 18` primitive is the only thing the components need to honor the four-props-shares contract from `packages/client/AGENTS.md`.

Icons are inline SVG (`ChevronRight`, `FolderIcon`, `FileIcon` in `FileTreePanel.tsx`) and the editor's "save" control is a plain `<button>`. The package depends on `clsx` for class composition and on `@deepseek-ai/dsh-client-ui-{connection,locale,runtime,ui-conversation,ui-layout,ui-sidebar}` only through `dsh.client.inject` (informational dependency edges, not Cordis activation order). The slot registration is a single `ctx.slots.register({ name: 'shell.tab.creator-workbench', store: { fileTree, editor, pipeline } }, Component)` call inside `ctx.effect()`, gated by a try/catch so a slots service that is not mounted (the headless smoke harness) is a no-op rather than a load error.

`apply()` itself is empty on the host half (`src/index.ts`); the browser half is `src/client/index.ts`, and the package is wired into the dsh-web bundle through the standard three registration surfaces: `tsconfig.client.json` aggregate references (added to the package's `tsconfig.json` and the root `tsconfig.client.json`); a `dsh.client` row in the package's `package.json` declaring `platform: 'web'` and the `inject` list; a dependency on `@deepseek-ai/dsh-client-ui-creator-workbench` in `packages/bundle/web-app/package.json` so the workspace's `node_modules/@deepseek-ai/...` resolution finds the row. The `dsh.client` row's platform value drives the client-plugin scanner, and the `./client` export (`lib/client.js`) is the dynamic bundle that ships to the browser.

## Alternatives considered

**One DSH client package per workbench column (`dsh-client-ui-creator-workbench-tree`, `dsh-client-ui-creator-workbench-editor`, `dsh-client-ui-creator-workbench-pipeline`).** Three smaller packages that compose through slots, each reusable independently. Rejected because (a) the three stores have no consumer outside the workbench, (b) the slot composition would force every user to register three slots in the right order, and (c) splitting raises the test surface from 3 specs to 9 with no behavior change. The single-package composition is the same slot registration; the difference is who is responsible for keeping the three stores in sync.

**Zustand for state management.** The runtime package already uses zustand, so adding it to the workbench feels like the natural fit. Rejected because zustand is a runtime-layer concern (the data object layer) and the workbench state is a per-tab viewing concern that lives entirely in the presentation tier. Importing zustand into the browser half would also require a `dsh.client.external` entry — zustand is a non-baseline dynamic request — and the verification-client-packages script enforces that. The hand-rolled `useSyncExternalStore` adapter is 60 lines, has no third-party surface, and runs on the platform's own React primitive.

**Render the three columns inside the existing conversation surface (right-side drawer).** It would have meant no new tab, no new slot, and no client package at all. Rejected because the conversation drawer is 320px wide and scrolling, the file tree alone wants 240px of static width, and rendering three columns inside a 320px drawer requires CSS magic that hides the editor and the pipeline on most screens. The tab gives the workbench a real canvas, and the user keeps the conversation drawer for the model-driven phase.

## Consequences

The workbench tab is opt-in: a profile that does not depend on the bundle's web-app patch will never see it, and the dsh-web profile picks it up automatically because the dependency is now part of the bundle's `package.json`. Three consequences follow. First, the workbench state is per-tab, not per-session: opening a new tab gives a fresh `createFileTreeStore()` / `createEditorStore()` / `createPipelineStore()` triplet, and closing a tab lets the React fiber dispose, which means the host does not need to think about cross-tab state leakage. Second, the package can be removed by deleting the bundle dependency and a one-line `tsconfig.client.json` entry; the runtime vocabulary the workbench exposes (`shell.tab.creator-workbench`) is a single slot name with no schema. Third, `useSyncExternalStore` means the components re-render on snapshot change without manual subscription bookkeeping, and the `actions` handle stays referentially stable so child components that depend on `store.actions.foo` do not re-render on every parent tick.

The component suite runs three jsdom specs (default mount, pipeline status update, file open through the tree) and takes 11 seconds on first run for the jsdom environment boot. The inline SVG icons are a minor visual regression against the rest of the dsh-web surface, which uses the `@deepseek-ai/dsh-client-ui-primitives` icon set; production wiring would replace them once the primitives ship a stable surface for the three glyphs (chevron-right, folder, file).
